## Approved Architecture

- The existing `execution` table is the authoritative durable queue and business lifecycle record.
- `execution_lease` is the current renewable runner-ownership record.
- Claim is the acquisition operation; lease is persisted ownership.
- A `PENDING` execution initially has no lease.
- The first claim atomically creates the lease and performs `PENDING -> CLAIMED`.
- One execution has at most one lease row.
- Reclaim updates the existing lease rather than storing ownership history.
- Queue selection uses PostgreSQL `FOR UPDATE SKIP LOCKED`.
- Queue ordering is `requested_at ASC, id ASC`.
- Ownership requires runner ID plus an unpredictable claim token.
- Claim tokens fence stale ownership epochs.
- Lease generation increments on reclaim.
- PostgreSQL time controls claim, heartbeat, expiry, and reclaim.
- Heartbeats use lease-local concurrency and do not modify `Execution.version`.
- Reclaim applies only while the execution remains `CLAIMED`.
- PostgreSQL is the only durable coordination mechanism.
- Prefer a unidirectional `ExecutionLease -> Execution` persistence relationship.

## Exact Scope Boundary

AS-019 owns:

- Initial queue claiming.
- `PENDING -> CLAIMED`.
- Current renewable leases.
- Heartbeat renewal.
- Claim-token fencing.
- Reassignment of expired leases while status remains `CLAIMED`.
- Internal claim and heartbeat protocol.

Deferred beyond AS-019:

- `CLAIMED -> RUNNING`.
- Complete runner orchestration and runner registration.
- Engine execution.
- Secret resolution.
- Runtime steps, results, logs, and artifacts.
- Execution attempts and lease history.
- Retries.
- Recovery of abandoned `RUNNING` executions.
- Cooperative cancellation completion.

- Do not use the lease as attempt or history storage.

## AS-019C - Atomic PostgreSQL Claiming

### Delivered

- Added a PostgreSQL-specific claim repository that selects only the oldest eligible execution ID
  using `FOR UPDATE OF execution SKIP LOCKED`.
- Preserved the approved queue order: `requested_at ASC, id ASC`.
- Restricted eligibility to `PENDING` executions without an `execution_lease` row.
- Added a transactional claim service that loads the locked execution through JPA, applies the

  first generation lease in the same transaction.
- Added server-generated unpredictable UUID claim tokens and validated trimmed runner IDs and
  positive lease durations capped at 24 hours.
- Used PostgreSQL `CURRENT_TIMESTAMP` as the authority for claim, heartbeat, and expiry timestamps.
- Returned an empty result when no execution is eligible.
- Changed lease audit timestamps to Hibernate database-sourced generation so lease ownership and
  audit time use the same database clock.
- Added focused unit and PostgreSQL Testcontainers integration coverage.

No controller or runner endpoint was added. Heartbeat, reclaim, retry, execution processing,
engine execution, artifacts, secret resolution, and later AS-019 phases remain unimplemented.

### Transaction, Version, and Persistence-Context Semantics

The native query selects only the execution UUID and acquires the PostgreSQL row lock; it does not
perform a native lifecycle update or materialize an `Execution`. The service then loads that row
through JPA and invokes the domain transition on the managed entity. This prevents a native update
from bypassing or leaving stale state in the persistence context.

The execution update is flushed before the lease insert. `Execution.version` advances exactly once
for `PENDING -> CLAIMED`; initial lease creation does not add another execution update. If lease
creation fails, the surrounding transaction rolls back both the lifecycle transition and lease
creation. A focused test preloads the pending execution into the persistence context and verifies
that the same managed object observes `CLAIMED` with one version increment.

### PostgreSQL Locking and Time

Concurrent claimers do not block one another on already locked candidates. Tests verify that one
execution receives only one owner, multiple queued executions can be claimed independently, and a
locked oldest candidate is skipped in favor of the next eligible row without arbitrary sleeps.
The pending queue query plan uses the V11 partial index `idx_execution_pending_queue`.

PostgreSQL may expose a native `CURRENT_TIMESTAMP` scalar as `Instant`; the claim repository
normalizes that value to UTC `OffsetDateTime` before applying the requested duration. Claim and
initial heartbeat timestamps are identical, expiry is derived from database time, and generation
starts at one.

## AS-019D - Lease Heartbeat Renewal

### Delivered

- Added an internal heartbeat command, service, immutable result, and typed failure categories.
- Added pessimistic lease and execution lookup methods for a short, serializable renewal
  transaction.
- Added a PostgreSQL-time repository for authoritative renewal and expiry evaluation.
- Validated execution ID, trimmed runner ID, claim token, positive generation, nonnegative expected
  lease version, and a positive lease duration capped at 24 hours.
- Added focused unit and PostgreSQL Testcontainers integration tests.

No HTTP endpoint, new claim token, ownership replacement, generation increment, reclaim, runner
registration, execution processing, or later-phase behavior was added.

### Algorithm and Transaction Boundary

The service validates the command, locks the lease by its execution primary key, and locks the
associated execution row. It then verifies runner ID plus claim token as one ownership credential,
lease generation, expected lease-local version, and `CLAIMED` lifecycle status. PostgreSQL
`CURRENT_TIMESTAMP` supplies the authoritative transaction time. Renewal requires the strict
condition `lease_expires_at > dbNow`.

On success, `last_heartbeat_at` becomes `dbNow`, `lease_expires_at` becomes
`dbNow + requested duration`, and Hibernate flushes the managed lease once. The existing
`@Version` mapping increments `ExecutionLease.version` exactly once. Runner ID, token, generation,
claim time, creation time, and all execution fields remain unchanged.

The locked-read design was selected over a single conditional native update because it preserves
precise failure categories without native entity mutation. Consequently, a previously managed
lease is the same object updated by the service and cannot remain stale. Locking the execution row
also ensures lifecycle eligibility is evaluated against serialized current state.

### Eligibility, Fencing, and Failures

The normative AS-019 heartbeat predicate permits only `CLAIMED`. `PENDING`, `RUNNING`,
`CANCEL_REQUESTED`, `PASSED`, `FAILED`, `CANCELLED`, and `ERROR` are ineligible. AS-019 does not
own the transition to `RUNNING`, and expired `RUNNING` recovery remains deferred.

Ownership requires exact execution ID, runner ID, claim token, and generation matches. The caller
also supplies the expected lease-local version. Failure categories distinguish lease not found,
combined ownership mismatch, stale generation, expired lease, ineligible lifecycle, optimistic
version conflict, and invalid request. Messages never contain the claim token. Heartbeat does not
return the token and never generates or replaces one.

### Concurrency and Persistence Context

Two concurrent renewals using the same expected lease version serialize on the lease row. Exactly
one succeeds and increments the lease version; the second observes the new version and receives an
optimistic-lock conflict without automatic retry. A database transaction that expires a locked
lease wins before a waiting heartbeat, and the heartbeat then rejects the expired ownership.
Renewal of another lease proceeds independently. Tests coordinate with latches and bounded futures,
not sleeps.

The update is performed through the managed `ExecutionLease`, so no native update can bypass the
persistence context. A preloaded managed lease test verifies current heartbeat timestamps and
version after renewal, while the managed `Execution` retains its lifecycle status and version.

### Query Plan and Schema

Heartbeat lookup is by `execution_lease.execution_id`; PostgreSQL evidence confirms the existing
primary-key index `execution_lease_pkey` supports it. The execution lock likewise uses its primary
key. No new index or migration is required, and V11 remains unchanged.

## AS-019E — Lease Expiration and Reclaim

### Scope and Design

AS-019E adds an internal queue-style reclaim operation only. Reclaim eligibility is exactly an
existing lease whose execution remains `CLAIMED` and whose
`lease_expires_at <= CURRENT_TIMESTAMP`. `PENDING`, `RUNNING`, `CANCEL_REQUESTED`, `PASSED`,
`FAILED`, `CANCELLED`, and `ERROR` are excluded. Recovery of abandoned `RUNNING` work remains
deferred.

The repository uses a native PostgreSQL candidate query ordered by
`lease_expires_at ASC, execution.requested_at ASC, execution.id ASC`, with
`FOR UPDATE OF lease, execution SKIP LOCKED LIMIT 1`. This locks both coordination rows, permits
parallel workers to skip locked work, and prevents two committed ownership transfers for one
lease. The service then loads the locked lease as a managed JPA entity, rechecks lifecycle and
expiry, obtains PostgreSQL `CURRENT_TIMESTAMP`, creates a server-side UUID through the existing
`ClaimTokenGenerator`, and invokes the lease domain reclaim operation.

The hybrid native-selection/managed-mutation design avoids persistence-context staleness and lets
Hibernate's `@Version` update `ExecutionLease.version` exactly once. There is no native update and
no entity-manager clear after selection. `Execution` is loaded through the lease relationship but
never mutated, so its status, version, snapshots, request metadata, relationships, and business
fields remain unchanged.

### Ownership Transfer, Result, and Failures

Successful reclaim updates the existing lease row. It replaces runner ID and claim token,
increments `lease_generation` exactly once, resets `claimed_at` and `last_heartbeat_at` to the
database reclaim time, and derives `lease_expires_at` from that time plus the validated duration.
The lease creation timestamp is preserved and the database-sourced update timestamp advances.
Generation uses Java `long`/PostgreSQL `BIGINT`; `Long.MAX_VALUE` fails before token generation or
mutation and cannot wrap.

Rotating the token and advancing generation permanently fence every previous owner. Integration
coverage verifies old credentials fail heartbeat while the new owner can renew. Tokens are absent
from exception messages and public DTOs, are never logged, and cannot be supplied by the reclaim
caller. The internal immutable `ReclaimedExecutionLease` returns the new token plus execution
dispatch identifiers, lifecycle/version metadata, lease timestamps/version, and defensive
immutable copies of the sanitized snapshots. Reclaim returns `Optional.empty()` when no unlocked
expired `CLAIMED` work exists.

Internal failures distinguish missing locked lease, active lease on under-lock recheck,
ineligible lifecycle, generation overflow, optimistic/concurrent conflict, token generation, and
persistence failure. Invalid runner IDs and durations use the existing request-validation
convention. Token generation and persistence occur inside one short Spring transaction; failures
roll back the complete ownership change and there is no automatic retry or external call.

### Concurrency, Persistence, and Index Review

Concurrent reclaimers use `SKIP LOCKED`: with one expired lease, only one ownership epoch is
committed and the other invocation observes no work; with multiple expired leases, workers
commit different leases and unique tokens. Heartbeat and reclaim serialize on the same lease and
execution rows: a committed heartbeat makes the candidate active, while a reclaim rotates the
credentials before an old heartbeat can succeed. Lifecycle changes serialized through the
execution row make reclaim revalidation fail once the execution is no longer `CLAIMED`.

V11 already provides `idx_execution_lease_expiry (lease_expires_at, execution_id)`, the execution
primary key/status data needed by the join, and both primary keys used for locked lookups. The
expiry index matches the leading filter/order columns; the remaining deterministic tie-breakers
come from the joined execution. No evidence justified another index or migration, so V11 remains
unchanged.

Concrete PostgreSQL 16 `EXPLAIN` evidence was captured for the production query shape:
`execution_lease` joined to `execution`, filtered by `status = 'CLAIMED'` and
`lease_expires_at <= CURRENT_TIMESTAMP`, ordered by expiry, request time, and execution ID, then
locked with `FOR UPDATE OF lease, execution SKIP LOCKED LIMIT 1`. With the focused one-row fixture
and sequential scans disabled, PostgreSQL selected
`idx_execution_status_requested_at` for the eligible execution scan and
`execution_lease_pkey` for the one-to-one lease lookup, applied the expiry predicate as a filter,
and used an explicit `Sort` for the complete deterministic order. The existing
`idx_execution_lease_expiry` remains available for expiry-led plans as table cardinality and
selectivity change. At the current expected scale, both join directions have appropriate indexes,
the result is bounded to one row, and the required cross-table tie-break order still needs a sort;
another index would duplicate existing coverage without eliminating that join-dependent sort.

### Dedicated Heartbeat-versus-Reclaim Race

Both scenarios exercise the real `ExecutionHeartbeatService`, `ExecutionReclaimService`, and
PostgreSQL row locks in independent transactions. Coordination uses explicit row locks, latches,
and futures whose waits are bounded at ten seconds; there are no sleeps or unbounded waits.

In the heartbeat-wins scenario, a test transaction first locks the lease and execution rows so the
heartbeat is known to be waiting on production locking. Releasing those locks lets heartbeat
renew and commit before reclaim evaluates eligibility. Reclaim then returns `Optional.empty()`.
The original runner and token remain authoritative, generation remains one, the lease version is
one from heartbeat alone, expiry is `database heartbeat time + duration`, and execution status
and version remain unchanged.

In the reclaim-wins scenario, the test token generator provides a latch after reclaim has locked
and validated the expired candidate. The old-owner heartbeat starts while reclaim holds those
locks. Releasing token generation lets reclaim commit the new runner, token, generation two, and
lease version one. The waiting old heartbeat then fails with ownership mismatch without revealing
either token and leaves the reclaimed row unchanged. A heartbeat using the new runner, new token,
generation two, and expected version one succeeds, advances only the lease version to two, and
keeps generation two. Execution remains `CLAIMED` at its original version throughout.

## AS-019F — Runner Claim and Heartbeat API

### Scope and Contract

AS-019F exposes the existing claim, heartbeat, and reclaim application services through three
runner endpoints:

- `POST /api/v1/runners/claim`
- `POST /api/v1/runners/heartbeats`
- `POST /api/v1/runners/reclaim`

Claim and reclaim accept a validated runner ID and ISO-8601 lease duration, return the immutable
dispatch snapshot and current lease ownership on success, and return `204 No Content` when no
eligible work is available. Heartbeat accepts the execution ID, runner ID, claim token, lease
generation, expected lease version, and duration. Its response contains only renewed lease
metadata and deliberately does not echo the claim token or runner ID.

The claim result contract now includes the initial persisted lease version (`0`), matching the
reclaim and heartbeat fencing contracts. MapStruct owns request-to-command and result-to-response
mapping. Request validation and malformed JSON/UUID/duration failures map to `400`; ownership,
expiry, lifecycle, stale-generation, and optimistic-lock failures map to `409`; only a genuinely
missing execution or heartbeat lease maps to `404`; unexpected and infrastructure failures retain
the sanitized `500` convention. Runner
authentication remains explicitly deferred with a controller TODO requiring a future principal
to be bound to `runnerId`.

Claim tokens occur only in claim/reclaim ownership responses and the heartbeat request. They are
never included in heartbeat responses or error bodies. Custom request/response `toString()`
implementations omit tokens so Spring MVC debug logging cannot disclose them. Runner-ID and token
mismatches intentionally share the same generic ownership-credentials message, so the response
does not reveal which credential was incorrect.

`ClaimedExecution.leaseVersion` is sourced from the managed `ExecutionLease` after
`ExecutionLeaseRepository.saveAndFlush`; it is not hardcoded or independently inferred. Unit
coverage makes the flush return a non-default entity version and verifies that exact version is
propagated. PostgreSQL integration coverage compares the API/result value with the committed
`execution_lease.version`, renews using that returned value, and verifies reuse becomes a `409`
stale-version conflict after heartbeat advances it.
