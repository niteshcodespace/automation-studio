## AS-030A - Karate Requirements and Execution Security Architecture

AS-030A creates repository authority for an API-only Karate v1. Karate UI/browser execution is
deferred because Playwright already owns browser execution and UI would add driver, process,
filesystem, and network authority to the first Karate boundary.

### Architecture decisions

- Plan `engines/karate-engine-plugin` as an SDK-dependent sibling provider module.
- Keep Karate dependencies and native types provider-local.
- Let `studio-api` depend on the future provider only for static assembly.
- Preserve one registry, orchestrator, lifecycle/fencing path, persistence model, workspace
  manager, secret scope, and AS-028 artifact authority.
- Require no SDK, database, Flyway, API, frontend, or infrastructure change for the approved v1.
- Treat JUnit and HTML as evidence formats, never execution-state authority.

### Security decisions

Karate features, configuration, JavaScript, calls, and reads are trusted executable repository
automation code, not passive manifests or safely contained hostile tenant input. AS-030 v1 uses
strict capabilities and ceilings but does not claim in-process isolation. Hostile or multi-tenant
execution requires a future process/container design.

Normal API-test JavaScript may be supported, while arbitrary Java host interop, reflection,
classpath extension, system/environment access, shell, and process creation are prohibited.
Technical enforceability is an AS-030C gate. Source access stays repository-relative below one
admitted root with traversal/link/file/count/depth limits.

API traffic requires AS-029-equivalent security outcomes: approved exact origin, address policy,
DNS-rebinding resistance, redirect/proxy/TLS controls, deadlines, and size/resource bounds. No
assumption is made that Karate can reuse or reproduce AS-029 DNS pinning; AS-030C must prove the
client interception/customization or stop.

Secrets resolve after target authorization at an attempt-local request sink and never become
ordinary Karate variables or native report state. Operator ceilings dominate suite parallelism.
Reports are rebuilt from an allowlisted sanitized model and publish only through AS-028; native
unsanitized output is prohibited.

## AS-030B blocker resolution - prepared-source listing capability

AS-030B has not started. Pre-implementation inspection confirmed that `WorkspaceAccess` could
open a prepared-source handle and `PreparedSourceAccess` could open one known repository-relative
path, but the SDK exposed no bounded directory listing or safe entry metadata. Structural feature
discovery therefore could not be implemented without a provider-neutral contract decision.

Four designs were compared: unbounded `list(directory)`, bounded `list(directory, maxEntries)`,
recursive `walk(directory, depth/count)`, and an iterator/stream. The selected operation lists one
directory with a positive explicit maximum and returns an immutable deterministic collection.
Caller-controlled composition keeps recursion and depth policy outside the generic provider;
unlike an iterator it creates no resource lifetime, and unlike `walk` it grants no implicit
recursive authority.

The SDK adds JDK-only immutable `PreparedSourceEntry` and `PreparedSourceEntryKind` values. Entries
contain only a validated repository-relative logical path, structural kind (`FILE`, `DIRECTORY`,
`LINK`, or `UNSUPPORTED`), and file size or an explicit unknown sentinel. The interface default
fails closed as unavailable, preserving existing implementer compatibility. The local platform
adapter validates root-relative directories, rejects absolute/traversal paths, enforces a maximum
of 10,000 direct entries per call, closes directory handles, sorts logical paths, reads metadata
without following links, surfaces links without targets, and returns immutable results. Physical
roots and provider exceptions remain internal.

Generic conformance fixtures and local adapter tests cover value validation, root/nested/empty
listing, deterministic ordering, file/directory/link classification, size metadata, immutable
results, traversal and absolute rejection, entry overflow, closed handles, concurrent handles,
and existing `open(path)` behavior. Focused verification built SDK, conformance, REST Assured, and
`studio-api`: 25 tests passed with zero failures/errors and 6 environment-dependent symlink skips.

The full six-module `mvn clean verify` compiled all production and test sources. SDK/conformance,
sample, and REST Assured completed 62 tests with zero failures/errors/skips before existing
`studio-api` Testcontainers integration initialization failed because no valid Docker environment
was available. The resulting integration errors are an infrastructure blocker and not reported as
a green full build.

Architecture review is `NONE`: the extension is JDK-only and provider-neutral, platform ownership
and one registry/orchestrator/lifecycle remain unchanged, and no Karate module, production
registration, persistence, or AS-030B/C work was added. Security review is `NONE`: logical paths,
limits, ordering, non-following link classification, metadata bounds, immutable returns, handle
closure, diagnostic containment, and concurrent isolation are covered. Compatibility review is
`NONE`: the default method preserves existing implementers and Builtin, Playwright, REST Assured,
sample, AS-028, registry, orchestrator, lifecycle, and zero-artifact behavior remain unchanged.

Changes are uncommitted and unpushed. AS-030B remains unstarted pending explicit approval after
this prerequisite is committed.

## AS-030B - Karate plugin module, discovery, and configuration contract

AS-030A and the prepared-source listing prerequisite are now committed and pushed. AS-030B adds
`engines/karate-engine-plugin` to the reactor without changing the SDK, conformance contracts,
registry, orchestrator, lifecycle, persistence, or artifact authority. The module declares
provider-local `io.karatelabs:karate-core:1.5.2`; the only other production dependency is the
JDK-only engine SDK, while generic conformance and JUnit are test-only. No browser or WebDriver
dependency is declared.

The immutable schema-1 configuration admits one bounded repository-relative feature root, exact
include/exclude tag declarations rather than tag expressions, bounded non-secret variable values,
logical secret references, and discovery limits no greater than operator ceilings. Strict parsing
rejects unknown fields, unsupported schema versions, malformed paths, traversal, drive-qualified
or backslash paths, NUL/blank values, duplicate identifiers/tags, ambiguous include/exclude tags,
reserved variable names, and invalid limits. Logical secret references remain inert and no secret
is resolved or materialized.

Feature discovery uses only bounded one-directory `PreparedSourceAccess.list(...)` calls and safe
entry metadata. It recursively sorts logical entries, selects `.feature` files, and enforces depth,
per-listing entry, feature-count, individual-byte, and aggregate-byte bounds. Links, unsupported
entry kinds, unavailable listing, malformed provider entries, and empty selection fail closed with
stable sanitized codes. Feature contents are not opened because AS-030B needs only structural
admission. Handles close deterministically.

The plugin descriptor identity is `karate:1.5.2`. Its minimal `execute(...)` conformance proof
performs configuration parsing and discovery only, then returns a correlated `SUCCEEDED` result
for successful structural preparation. This state describes the provider operation, not execution
of Karate scenarios. There is no HTTP/DNS activity, secret access, process or browser authority,
artifact publication, production registration, or AS-030C runtime behavior.

Focused verification built the SDK, generic conformance, and Karate provider modules. The generic
module ran 17 tests and the provider ran 18 tests: 35 total, zero failures, errors, or skips, and
`BUILD SUCCESS`. An initial full run encountered an unchanged runner lease-timing error. The exact
runner test then passed alone (1 test, zero failures/errors/skips), and the one authorized full
retry completed all seven modules: 1,258 tests, zero failures/errors, 18 skips, `BUILD SUCCESS`.

Architecture review is `NONE`: module placement and dependency direction are correct, SDK and
conformance stay provider-neutral, and registry/orchestration/lifecycle/persistence remain
unchanged. Security review is `NON-BLOCKING`: discovery and configuration fail closed and the B
implementation exercises no Karate runtime authority, while Karate Core's broad transitive

## AS-030C1 - isolated runtime architecture / blocker resolution

AS-030C stopped before implementation after inspection of Karate 1.5.2 showed that its internal
GraalJS context calls `allowAllAccess(true)`, enables Nashorn compatibility, and has no supported
runner hook for a replacement host-access policy. Feature-visible bridge methods include process,
property, filesystem, listener and other host operations. Static filtering, reflection patches or
deployment policy cannot satisfy ADR-020, so no in-process execution was accepted.

A child JVM and an isolated container were compared. A child JVM gives classpath and environment
separation plus straightforward kill semantics, but its working directory is not a filesystem
boundary; process creation and network denial need different OS mechanisms on Windows and Linux;
heap flags do not enforce CPU, PID or disk ceilings; and it retains host access under the runner
identity. It is insufficient for v1. The selected design is one pinned short-lived Linux container
per invocation. It runs a fixed entrypoint as non-root with a read-only root, dropped capabilities,
no-new-privileges, scrubbed environment and properties, no Docker socket or host mounts, bounded
tmpfs, memory/CPU/PID/output limits, and an execution-specific network namespace. This limits
trusted automation authority but is not certified hostile multi-tenant isolation.

The provider reads only admitted exact-revision entries through `PreparedSourceAccess`, computes
sizes and digests, and sends a bounded manifest and file frames over versioned length-prefixed JSON
stdin. The worker independently validates correlation, schema, paths, sizes and digests and builds
its repository-relative tree in tmpfs; no platform path crosses the boundary. Stdout returns only
bounded correlation, normalized status/counts and diagnostic categories. Unexpected or oversized
frames fail closed, and capped stderr is never relayed raw. Workspace Manager retains preparation
and cleanup authority; the provider additionally removes the container, tmpfs, network and gateway
idempotently in `finally`.

Direct worker egress is denied. Its only peer is a platform-owned per-execution gateway that
authorizes every normalized HTTP(S) origin and attempt, validates all DNS answers, connects to one
selected address without re-resolution, rejects redirects for C3 v1, rejects proxy bypass, and enforces
request, response, decompression and monotonic deadline limits. The gateway independently validates
upstream hostname and certificate; an execution-scoped worker trust anchor prevents Karate
trust-all settings from bypassing upstream policy. Deployment egress is defense in depth, not the
application authorization mechanism.

Future AS-030D secrets remain outside the worker. The feasible sink is the gateway: after target
authorization it can request one attempt-local value through a bounded provider-owned broker,
inject it at dispatch, close it on every outcome, and never return it over worker IPC. AS-030E
evidence will cross as a bounded sanitized model and publish only through `ArtifactPublisher`; the
worker never receives storage or metadata authority.

The SDK remains unchanged. The provider owns worker mechanics behind `ExecutionEnginePlugin`; the
canonical orchestrator and runner lifecycle remain unchanged. Delivery is split into AS-030C1
architecture, AS-030C2 isolated runtime foundation without Karate execution, and AS-030C3
controlled sequential Karate execution. AS-030D depends on C3 and has not started.

Security review is `NONE` for the design: host classpath, environment, filesystem, process, IPC,
network, DNS, TLS, termination, future secret and artifact boundaries fail closed in the selected
model. Implementation evidence remains mandatory in C2/C3. Architecture review is `NONE`: SDK,
Workspace Manager, registry, orchestrator, lifecycle, persistence and AS-028 ownership stay
unchanged. Compatibility review is `NONE`: Builtin, Playwright, REST Assured, sample, AS-027,
AS-028, current APIs, persistence and zero-artifact behavior are unaffected. Required v1 deployment
impact is a supported Linux-container runtime, digest-pinned worker image, controlled
gateway/network, syscall/LSM process restrictions, resource-limit support and orphan cleanup.
Rootless runtime, stronger image attestation, Kubernetes and hostile-source certification are
future hardening.

### AS-030C3 architecture decision - external worker containment

Option B is approved. The isolated disposable worker container, not Karate 1.5.2's GraalJS context,
is the Java/process authority boundary. Runtime-local `Java.type`, `karate.exec`, and `karate.fork`
may exist, but must not reach Automation Studio or Spring classes/services, host files or
environment, credentials, Docker control, host processes, unrestricted network, cross-execution or
persistent state. This reconciles the ADR with the existing trusted-repository automation model; it
does not claim hostile multi-tenant sandbox certification.

AS-030C3 external-worker containment is now implemented under Option B. Worker and gateway creation
explicitly apply the built-in seccomp profile, no-new-privileges, dropped capabilities, non-root
identities, read-only roots, private PID/network boundaries and bounded resources. Projected source
is sealed to owner-read-only files and owner-read/execute directories, while independent bounded
runtime and temporary tmpfs mounts remain writable. Gateway redirects are rejected without
contacting the redirect target. Lifecycle command timeouts are enforced while output is drained,
and cleanup attempts every created worker, gateway and network before reporting an orphan.

The opt-in real-container proof passed on Docker Desktop Engine 29.6.1 using immutable local worker
and gateway image IDs. It proved source write/delete/move denial, bounded runtime writability,

host workspace, Docker socket, credential/proxy environment and direct egress, gateway-only reach,
successful protocol execution and post-run resource absence. Docker advertised built-in seccomp
and cgroup namespaces but no AppArmor or SELinux LSM, so no additional LSM was applicable in this
environment. Secrets, parallelism, artifacts, production registration, and AS-030D/E/F remain
excluded.

Final C3 verification passed. Focused module evidence comprises conformance 17/0/0/0,

### AS-030D1 - execution-scoped secret handling

AS-030D1 now reuses the existing provider-neutral `ExecutionSecretAccess` and closeable
`ResolvedSecret` capability without changing the SDK or platform secret authority. Suite
configuration contains bounded logical aliases plus one strict authentication declaration: none,
bearer, basic, API-key header, or API-key query. Logical provider references remain in the trusted
provider and neither references nor values enter worker IPC, variables, source, environment,
container arguments, metadata, results, diagnostics, reports, artifacts, or persistence.

The provider owns an execution-local broker over the gateway's private interactive attach channel.
The gateway receives only non-secret mode/placement metadata at startup. For every request it first
normalizes and authorizes the origin, resolves and validates DNS addresses, and rejects header or
query collisions. Only then does it request fresh material from the provider, inject it immediately
before dispatch, and clear request-scoped character buffers on success, transport failure, timeout,
redirect rejection, interruption, or protocol failure. SDK secret objects and exceptional partial
copies close deterministically. Gateway retries remain disabled, and redirects remain rejected.

D1 remains sequential and adds no scheduling, artifacts, registration, persistence, or lifecycle
path. AS-030D2/D3 and AS-030E/F have not started.

D1 focused verification initially passed across SDK, conformance, worker, gateway and provider: 61
tests, zero failures, zero errors and two skips, `BUILD SUCCESS`. The initial exact-current-source
isolated full reactor passed with 1,284 tests, zero failures, zero errors and 20 skips, `BUILD
SUCCESS`.

A subsequent independent security review found a blocking credential-authority defect: removing
the transport's unconditional `Authorization` rejection allowed worker-supplied `Authorization`
headers through in none and API-key modes. The remediation reserves `Authorization`
case-insensitively during authentication preflight for every mode, before broker materialization.
Regression coverage proves fail-closed behavior for none, bearer, basic, API-key header and API-key
query modes, including case variants and duplicate names, with zero secret materializations and
sanitized diagnostics. Post-remediation focused verification passes 63 tests with zero failures,
zero errors and two skips. The post-remediation exact-current-source isolated full reactor passes
1,286 tests with zero failures, zero errors and 20 skips across nine modules, `BUILD SUCCESS`.
Security, architecture and compatibility review findings are `NONE` after remediation; AS-030D2
remains unstarted.

## AS-030D2 - bounded parallel runtime execution

The D2 configuration contract and runtime wiring are repository-authoritative.
`KarateSuiteConfiguration` owns the sole suite request as top-level `parallelism`,
strictly accepts integer values `1..8`, and defaults absence to `1`. Invalid, non-integral,
overflowing, malformed, and unsupported values fail closed with the sanitized
`INVALID_PARALLELISM` category. `WorkerLimits` owns the separate provider/runtime maximum, defaults
it to the immutable v1 ceiling `8`, and permits only `1..8`.

`DockerKarateWorkerRuntime` calculates
`min(suiteRequestedParallelism, runnerMaximumParallelism, 8)` exactly once and passes only that
bounded value to the worker and gateway. The worker uses Karate's native `.threads(value)`
scheduler. The result-identity remediation uses Karate's native `Scenario.getUniqueId()` and
`ScenarioResult`: a concurrent expected-ID set is populated in `beforeScenario`, a duplicate-safe
completion map is populated in `afterScenario`, and execution fails closed unless the two identity
sets are exactly equal. Identity-sorted internal results retain each native pass/fail association;
feature resource, section index, and outline example index keep duplicate names and Examples rows
distinct. Aggregate counts are derived from those retained results, and any assertion failure
produces `FAILED` regardless of completion order. Value `1` retains the existing sequential path.

The execution-scoped gateway holds a fair permit from authorization and late secret materialization
through outbound completion. The permit count equals effective scenario parallelism, uses the same
absolute execution deadline, and cannot be shared across executions. One worker, gateway, Docker
network, lifecycle, and deadline remain authoritative. Timeout or interruption still closes IPC,
terminates the worker and gateway, and removes the execution network in the provider `finally`
path. No SDK, orchestration, persistence, registry, Workspace Manager, artifact-ownership, or D1
secret-authority change is introduced. Final result-identity remediation focused verification
passed 76 tests with zero failures, zero errors, and two skips. The exact-current-source isolated
full reactor passed 1,299 tests with zero failures, zero errors, and 20 skips (`BUILD SUCCESS`).

## AS-030C2 - isolated runtime foundation

AS-030C2 implements the containment foundation without loading or executing Karate. The worker is
a separate JDK-only module and image with a fixed Java entrypoint, minimal jar-only classpath and
non-root UID/GID 10001. Its Eclipse Temurin 21.0.11+10 Alpine 3.23 base is pinned to immutable
index digest `sha256:704db3c40204a44f471191446ddd9cda5d60dab40f0e15c6507b815ed897238b`.
The provider requires a configured immutable worker image ID or repository digest and never
accepts a floating tag.

Provider-owned Docker creation uses no host mounts or Docker socket, `network=none`, a read-only
root, all capabilities dropped, no-new-privileges, fixed non-root identity, one CPU, 768 MiB
memory/no swap expansion, 128 PIDs and a 64-MiB noexec/nosuid/nodev tmpfs. Only a fixed locale is
passed from the runner; host credentials, HOME, Docker configuration, proxies and arbitrary JVM
properties are not inherited. Stdin/stdout use version-1 four-byte length-prefixed deterministic
JSON with 1-MiB frame/output caps, strict types, execution correlation and fail-closed malformed,
unknown, premature-EOF and unexpected-output handling. Stderr is discarded by the attached
process and bounded for lifecycle commands rather than relayed.

The provider opens discovered feature bytes only through `PreparedSourceAccess`, computes size and
SHA-256, and sends logical repository-relative paths; no physical path crosses IPC. The worker
independently validates paths, traversal/absolute/device-like representations, duplicates, size,
digest, per-file and 32-MiB aggregate ceilings before reconstructing source beneath execution-local
tmpfs. It returns only `READY`, `ACCEPTED_SOURCE`, `COMPLETED_FOUNDATION_PROOF` and `BYE` and removes
the projection on close. Timeout, interruption, protocol faults and worker exits close IPC and run
idempotent stop, hard-kill, force-remove and absence inspection. Direct network egress is disabled;
gateway dispatch remains deferred to AS-030C3.
