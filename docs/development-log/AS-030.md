## AS-030A - Karate Requirements and Execution Security Architecture

AS-030A creates repository authority for an API-only Karate v1. Karate UI/browser execution is
deferred because Playwright already owns browser execution and UI would add driver, process,
filesystem, and network authority to the first Karate boundary.

### Architecture decisions

- Plan `engines/karate-engine-plugin` as an SDK-dependent sibling provider module.
- Keep Karate dependencies and native types provider-local.
- Let `studio-api` depend on the future provider only for static assembly.
- Preserve one registry, orchestrator, lifecycle/fencing path, persistence model, workspace
  manager, secret scope, and AS-028 artifact authority.
- Require no SDK, database, Flyway, API, frontend, or infrastructure change for the approved v1.
- Treat JUnit and HTML as evidence formats, never execution-state authority.

### Security decisions

Karate features, configuration, JavaScript, calls, and reads are trusted executable repository
automation code, not passive manifests or safely contained hostile tenant input. AS-030 v1 uses
strict capabilities and ceilings but does not claim in-process isolation. Hostile or multi-tenant
execution requires a future process/container design.

Normal API-test JavaScript may be supported, while arbitrary Java host interop, reflection,
classpath extension, system/environment access, shell, and process creation are prohibited.
Technical enforceability is an AS-030C gate. Source access stays repository-relative below one
admitted root with traversal/link/file/count/depth limits.

API traffic requires AS-029-equivalent security outcomes: approved exact origin, address policy,
DNS-rebinding resistance, redirect/proxy/TLS controls, deadlines, and size/resource bounds. No
assumption is made that Karate can reuse or reproduce AS-029 DNS pinning; AS-030C must prove the
client interception/customization or stop.

Secrets resolve after target authorization at an attempt-local request sink and never become
ordinary Karate variables or native report state. Operator ceilings dominate suite parallelism.
Reports are rebuilt from an allowlisted sanitized model and publish only through AS-028; native
unsanitized output is prohibited.

### AS-030A scope and checkpoint

AS-030A changes documentation only: requirements, ADR-020, implementation plan, this log, and
minimum roadmap and architecture reconciliation. It creates no Java, tests, POM, dependency,
module, migration, runtime configuration, commit, push, or PR. AS-030B remains unauthorized.

Static verification uses `git diff --check`, status/stat review, and explicit documentation-only
scope inspection. Maven is intentionally not run. Security, architecture, and compatibility
reviews are recorded at the uncommitted checkpoint after the document set is complete.

### AS-030A review record

**Security review: NONE after resolution.** The review covered executable-source trust, Java and
JavaScript host authority, process execution, filesystem/link escape, SSRF and DNS rebinding,
redirect/proxy/TLS policy, secrets, resource exhaustion, cancellation, report leakage and active
HTML, cross-execution state, and dependency supply chain. It identified two documentation gaps:
dependency-tree/supply-chain review was implicit, and cancellation wording could imply an SDK
token that does not exist. Requirements now make dependency review explicit, define deadline and
runner-interruption behavior as the current minimum, and require separate provider-neutral review
for any new cancellation capability. No blocking AS-030A finding remains.

**Architecture review: NONE.** The planned provider module owns Karate behavior and dependencies;
the SDK remains unchanged and JDK-only; `studio-api` is limited to static assembly; one registry,
orchestrator, lifecycle/fencing path, workspace manager, secret scope, artifact authority, and
persistence model remain. No UI/browser implementation, module, dependency, migration, or AS-030B
work is present. The A-F story boundaries remain intact.

**Compatibility review: NONE.** The documentation preserves AS-027 SDK/conformance, AS-028
artifact/evidence and zero-artifact behavior, AS-029 REST Assured, Builtin, Playwright, sample
plugin, exact registry resolution, canonical orchestration, runner lifecycle/fencing, existing
persistence, artifact discovery, and public APIs. No migration or compatibility action is required
by AS-030A.
