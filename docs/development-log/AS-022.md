# AS-022 - Runner Execution Orchestrator

## Feature

An engine-neutral runner execution layer that turns an AS-021 claim into a supervised automation
run, normalized evidence/results, and one fenced authoritative execution outcome.

## Objectives

- Preserve AS-018 immutable snapshots and lifecycle semantics.
- Preserve the AS-019 execution lease as the sole ownership and fencing model.
- Begin only after the AS-021 scheduling transaction has committed.
- Build one immutable runtime context and resolve secrets only at invocation time.
- Select engines through a stable provider-neutral contract.
- Supervise deadlines, lease renewal, cancellation, cleanup, results, evidence, and events.
- Keep all engine-specific logic outside orchestration.
- Defer retries, resume, distributed/parallel execution, and storage implementations.

## Architectural Decisions

### Preserve the existing durable lifecycle

`STARTING`, `EXECUTING`, `FINALIZING`, and cleanup are runner-local phases. They do not create a
second persisted lifecycle. Successful completion maps to `PASSED`, completed assertion failures
to `FAILED`, operational failures and timeout to `ERROR`, and cooperative cancellation to
`CANCELLED`.

### Build an immutable runtime context

The context loader validates and deep-copies admitted snapshots, ordered selections, Project
identity, deterministic variables, engine identity, runner metadata, ownership controls,
deadline, cancellation, and evidence policy. Mutable catalog data cannot redefine admitted work.
Resolved secrets remain in a separate invocation-scoped sensitive view and are never persisted.

### Use a provider-neutral engine contract

Every engine declares a stable ID, implementation version, compatible contract versions, and
capabilities. Exactly one provider is selected by exact engine ID and contract compatibility.
Engines validate and execute a context, receive cancellation, emit normalized results/evidence,
and clean up. They cannot access platform repositories, ownership credentials, arbitrary secrets,
or authoritative lifecycle transitions.

### Keep orchestration runner-mediated

The orchestrator sequences context preparation, provider selection, fenced start, execution,
lease supervision, cancellation, normalization, fenced finalization, post-commit events, and
cleanup. It owns failure precedence and contains no Playwright-specific path.

### Preserve lease ownership and short transactions

`execution_lease` remains the only ownership record. Start and terminal writes validate the full
fencing tuple and current execution state in short transactions. External secret, workspace,
engine, evidence, and event work occurs outside database transactions.

The current AS-019 heartbeat is `CLAIMED`-only. AS-022C must deliberately reconcile renewal for
`RUNNING` and cooperative `CANCEL_REQUESTED` work while preserving PostgreSQL time, token,
generation, version, and lock-order safeguards.

### Normalize evidence behind ports

Logs, screenshots, stdout/stderr, console output, attachments, native reports, and metadata flow
through a bounded orchestrator-owned sink. Engines do not choose storage paths or write platform
tables. Byte storage, retention, video, and streaming remain deferred.

### Classify but do not retry

Assertion failure is a completed `FAILED` result. Startup, crash, timeout, infrastructure, and
unexpected failures are `ERROR`; cancellation is `CANCELLED`; lost ownership permits no stale
write. Retryability metadata is future policy input only. Persistence/upload retry must never
rerun the engine.

## Key Invariants

- A claim transaction commits before orchestration starts.
- Exactly one current execution lease authorizes work.
- Claim tokens never reach engines, logs, events, or evidence metadata.
- A stale runner cannot start, renew, or finalize.
- Engine ID and contract compatibility select a provider deterministically.
- Snapshot validation fails closed; mutable catalog state is not a fallback.
- Secret values are runtime-only and least-scoped.
- External work never holds scheduling locks or long database transactions.
- Engines emit facts; only the platform assigns authoritative outcomes.
- Cancellation and timeout cannot be overwritten by a late success callback.
- Cleanup is bounded and idempotent.
- No automatic execution retry occurs.

## Risks

- Extending lease renewal beyond `CLAIMED` without one reviewed lock order could introduce
  heartbeat, cancellation, and finalization races.
- Runner loss after `RUNNING` has no approved resume/retry/recovery policy yet.
- An in-process provider can affect runner stability until stronger isolation is approved.
- Weak provider output bounds could exhaust disk or memory.
- Secret redaction cannot compensate for giving an engine unnecessary secrets.
- Provider ambiguity or contract drift could make admitted work unexecutable.
- Evidence storage and event delivery failures need explicit policy so they do not silently
  rewrite valid test results.
- Late engine callbacks must be fenced after timeout, cancellation, or ownership loss.

## Deferred Work

- Distributed execution, parallel execution, and remote execution clusters.
- Artifact/evidence storage implementation and retention.
- Video recording and live streaming.
- Plugin marketplace, dynamic installation, signing, trust, and isolation.
- Execution retries, attempts, resume, and orphaned-running recovery.
- Execution history UI.
- Source workspace and checkout implementation.
- Concrete secret provider and authorization enforcement.
- Durable event delivery/outbox.
- Final engine-contract code shape and result schemas.

## Implementation Safeguards

- Do not add provider-specific branching to the orchestrator.
- Do not pass repositories or lease credentials into an engine.
- Do not add a second ownership or business lifecycle model.
- Do not persist resolved secrets or raw sensitive context.
- Do not consult mutable suite/environment data as a snapshot fallback.
- Do not execute engines in a claim, heartbeat, REST, or persistence transaction.
- Do not finalize after any ownership fence fails.
- Do not map timeout or engine crash to assertion `FAILED`.
- Do not treat local phase telemetry as a resume checkpoint.
- Do not implement retries without an approved attempt/history design.
- Do not select providers by classpath order.
- Do not begin a later phase before the current review gate is approved.
