# AS-022 - Runner Execution Orchestrator

## Feature

An engine-neutral runner execution layer that turns an AS-021 claim into a supervised automation
run, normalized evidence/results, and one fenced authoritative execution outcome.

## Objectives

- Preserve AS-018 immutable snapshots and lifecycle semantics.
- Preserve the AS-019 execution lease as the sole ownership and fencing model.
- Begin only after the AS-021 scheduling transaction has committed.
- Build one immutable runtime context and resolve secrets only at invocation time.
- Select engines through a stable provider-neutral contract.
- Supervise deadlines, lease renewal, cancellation, cleanup, results, evidence, and events.
- Keep all engine-specific logic outside orchestration.
- Defer retries, resume, distributed/parallel execution, and storage implementations.

## AS-022B Implementation

### Immutable Context Model

AS-022B adds a provider-neutral `com.automationstudio.api.execution` model:

- `ExecutionContext` is the single top-level engine input and contains execution, Project, and
  Workspace identity; suite/environment snapshots; secret references; resolved variables;
  runner context; and execution metadata.
- `ExecutionEnvironmentSnapshot` and `ExecutionSuiteSnapshot` expose reviewed immutable
  snapshot values rather than JPA entities.
- `ExecutionRunnerContext` captures runner UUID/key, agent version, platform, capabilities, and
  labels at context-construction time.
- `ExecutionVariable` retains each winning value and its `ExecutionVariableSource`.
- `ExecutionSecretReference` retains admitted references only. AS-022B does not resolve or expose
  secret values.
- `ExecutionMetadata` provides deterministic correlation, creation/claim timestamps, timeout,
  and an explicitly disabled `ExecutionRetryPolicy`.

Every record constructor validates mandatory values and defensively deep-copies JSON-compatible
maps and lists into unmodifiable structures. Neither the context nor a nested value contains a
JPA entity or lazy association.

### Deterministic Variable Resolution

`ExecutionContextBuilder` parses only admitted environment, suite, and request snapshots. The
precedence from lowest to highest is:

```text
system defaults
    < Project defaults
    < Environment snapshot variables
    < Automation Suite snapshot variables
    < Execution request snapshot variables
```

AS-022B has no persisted system-default or Project-default variable source, so the service passes
empty maps for those two documented extension layers. Exact names in a higher layer replace the
lower value. Case-only name collisions are rejected as ambiguous duplicates; blank keys and null
values are invalid.

Environment/suite variables are read from `configuration.variables`; execution overrides are
read from `request_snapshot.variables`. Missing variable objects mean an empty layer. The
remaining provider-neutral configuration is retained separately.

### Validation and Defaults

The builder fails closed for missing/mismatched identities or snapshots, absent mandatory suite
or environment fields, malformed configuration/reference/variable objects, unsupported value
types, invalid/unsupported engine capability/version, ambiguous variables, invalid correlation
IDs, invalid timeout, and any retry policy other than disabled.

The canonical engine ID comes from the immutable suite snapshot. Its execution-time version is
the exact string advertised for that engine by the claimed runner. The optional request timeout
uses ISO-8601 duration syntax, defaults to 30 minutes, and is bounded to 24 hours. Correlation
defaults deterministically to the execution ID because no separate persisted correlation field
exists. Retry policy is always `DISABLED`; no retry behavior is introduced.

### Read-Only Context Service

`ExecutionContextService` and `ExecutionContextServiceImpl` load the existing execution,
execution lease, registered runner, Project/Workspace identity, and immutable snapshots in one
read-only transaction. The service requires `CLAIMED`, a current lease record, its registered
runner, and present relational Project, Workspace, Environment, and Automation Suite identities.

The service maps all entity values into `ExecutionContextSource` and passes that detached,
deep-copied source to the builder. JPA entities never cross the context boundary. Context creation
does not lock or mutate scheduling, lifecycle, runner, or lease state.

## AS-022C Implementation

### Provider-Neutral Engine Registry

AS-022C adds `com.automationstudio.api.execution.engine` as the startup-time extension point for
future providers. `ExecutionEngine` exposes only immutable descriptor discovery and deterministic
context validation; it has no execution method and no provider-specific behavior.

`ExecutionEngineDescriptor` identifies an engine by a case-sensitive name and exact version,
provides a display name, and publishes immutable capability and feature sets.
`ExecutionEngineRegistryImpl` receives the complete Spring-discovered engine list at
construction, validates every registration, and then stores only immutable maps and a sorted
immutable descriptor list. Consequently registration cannot change after startup and concurrent
lookups require no locking.

The registry:

- rejects null engines, null descriptors, and duplicate name/version pairs at construction;
- resolves exact name/version pairs independently of injection or classpath order;
- allows name-only resolution only when exactly one version is registered;
- distinguishes an unknown engine from an unsupported or ambiguous version;
- verifies the immutable context's exact engine name/version against the runner's advertised
  `capabilities.engines` entry; and
- delegates provider-specific preflight validation only after registry and runner compatibility
  have succeeded.

`ExecutionEngineSupport` returns the selected engine and its already-validated descriptor as one
immutable value. No concrete Playwright, Selenium, Karate, REST Assured, mobile, or performance
engine is registered by this story.

### Lease Reconciliation

The AS-019 heartbeat transaction retains its lease-then-execution lock order, runner ID and claim
token ownership checks, generation fence, lease-local optimistic version, strict database-time
expiry boundary, and database-time renewal.

Renewal eligibility now covers both persisted ownership states used by the orchestrator:
`CLAIMED` and `RUNNING`. The runner-local `STARTING` phase remains durably `CLAIMED`, as required
by the AS-022 lifecycle decision, so startup is covered without adding a persisted status or
changing the schema. Terminal, pending, and cancellation states remain ineligible. Scheduling,
claiming, lifecycle transitions, and REST contracts are unchanged.

### AS-022C Tests

Descriptor and registry tests cover null/blank validation, defensive immutability, duplicate
registration, deterministic listing, successful name and version lookup, unknown engines,
unsupported and ambiguous versions, and concurrent reads. Compatibility tests cover exact runner
engine/version matching, missing runner support, provider validation delegation, and context
immutability.

Heartbeat unit and PostgreSQL integration coverage verifies renewal in `CLAIMED` (including the
runner-local startup phase) and `RUNNING`, rejection of all other states, ownership and generation
fencing, optimistic conflicts, strict expiry, concurrent renewal, and non-mutation on failure.

AS-022C adds no database migration, REST/API change, scheduling change, provider execution,

## AS-022D Implementation

### Runner Execution Service

AS-022D adds `com.automationstudio.api.execution.orchestration` as the provider-neutral
coordination boundary between an owned claim and future engine execution.
`RunnerExecutionService` exposes two operations:

- `start` performs the fully fenced `CLAIMED` to `RUNNING` transition after building and
  validating the immutable context and resolving an exactly compatible engine.
- `prepareCompletion` proves that the caller still owns a valid `RUNNING` execution and returns
  immutable preparation metadata without assigning a terminal outcome.

`RunnerExecutionRequest` carries the complete caller fence: execution ID, runner ID, claim token,
lease generation, expected lease version, and expected execution version. Start and completion
results intentionally omit the claim token. `ExecutionStartResult` returns the immutable context
and selected descriptor for a later invocation story, but never invokes the engine.

### Centralized Ownership and State Validation

`ExecutionOwnershipValidator` fails closed unless all ownership dimensions match:

- the request, lease, lease association, and execution identify the same execution;
- runner ID and claim token match;
- lease generation and lease-local optimistic version match;
- execution optimistic version matches; and
- lease expiry is strictly after PostgreSQL database time.

Errors never include the claim token. `ExecutionStateValidator` admits only `CLAIMED` for start
and only `RUNNING` for completion preparation. Consequently duplicate start, pending work,
terminal work, and cancellation states fail without engine validation or lifecycle mutation.

### Fenced Start Transaction

The service uses the existing AS-019 lock order:

```text
lock execution_lease
    -> lock execution
    -> read PostgreSQL time
    -> validate ownership and optimistic fences
    -> validate CLAIMED state
    -> build immutable ExecutionContext
    -> resolve and validate ExecutionEngine
    -> transition execution to RUNNING
    -> flush the versioned execution row
```

The shared lease lock query now locks only `execution_lease`; the subsequent explicit execution
lock loads the execution row after any lease-lock wait. This avoids retaining a pre-wait
`JOIN FETCH` execution snapshot in the persistence context. The existing heartbeat PostgreSQL
concurrency suite verifies that this tightening preserves lease renewal behavior.

The engine contract exposes validation only, so no external provider work occurs. Concurrent
starts serialize on the lease row; the winner changes the execution to `RUNNING`, while a later
caller fails its execution-version or state fence. Engine discovery or compatibility failure
occurs before the lifecycle mutation and rolls the transaction back.

### Completion Preparation

Completion preparation takes the same locks and validates the same ownership, generation,
version, and expiry fence. It requires `RUNNING`, returns the database preparation time, and does
not change execution status, persist an outcome, delete the lease, collect evidence, create
artifacts, publish events, or invoke cancellation behavior.

## AS-022E Implementation

### Provider-Neutral Invocation

`ExecutionEngine` now has one provider-neutral `execute(ExecutionContext)` entry point returning
an immutable `ExecutionResult`. The contract contains no Playwright, Selenium, Karate, REST
Assured, evidence, artifact, logging, retry, timeout, cancellation, or event API.

`ExecutionEngineInvoker` is the deliberately small invocation boundary. It knows only how to
call the selected engine with the immutable context; it has no repository or ownership access.
Engine implementations therefore cannot make authoritative lifecycle transitions.

### Execution Lifecycle

`ExecutionLifecycleService` composes the already-fenced AS-022D operations:

```text
fenced start (CLAIMED -> RUNNING, commit)
    -> resolve the already-validated engine
    -> invoke engine outside a transaction
    -> validate or normalize its immutable result
    -> fenced completion (RUNNING -> PASSED/FAILED, commit)
```

The completion request carries forward the execution version returned by `start` and repeats
runner, claim-token, generation, lease-version, execution-version, expiry, and state validation.
Lease loss or any stale fence after provider invocation prevents the terminal write. The shared
lease-then-execution lock order remains unchanged.

Lifecycle `SUCCEEDED` maps to the existing persisted `PASSED` status and lifecycle `FAILED` maps
to persisted `FAILED`. This preserves the AS-018 database lifecycle and requires no migration.
The lifecycle result contains only orchestration identity, status, timestamps, duration,
termination/failure classifications, and immutable string metadata.

### Result and Failure Normalization

`ExecutionLifecycleValidator` rejects null results, mismatched execution/runner identity,
non-terminal results, and inconsistent duration. Provider exceptions never leave the lifecycle
boundary: they become `FAILED` results with `ENGINE_EXCEPTION`; malformed provider results become
`INVALID_ENGINE_RESULT`; provider-declared failures retain `ENGINE_REPORTED_FAILURE`.
Provider exception text and types are not copied into result metadata.

AS-022E intentionally supports only `RUNNING -> SUCCEEDED` and `RUNNING -> FAILED`. Finer
operational `ERROR` classification, timeout supervision, cancellation coordination, retry,
evidence/artifact ports, and event publication remain future work.

### AS-022E Tests

Unit coverage verifies successful invocation, provider-declared and thrown failures, exception

## AS-022F Implementation

### Provider-Neutral Evidence Model

AS-022F adds `com.automationstudio.api.execution.evidence` as an immutable, provider-neutral
boundary between execution engines and future artifact storage. `ExecutionEvidence` contains only
execution and runner identity, capture time, immutable artifact references, immutable string
metadata, and an `ExecutionEvidenceSummary`.

`ExecutionResult` now carries evidence alongside its existing orchestration outcome. Its
backward-compatible constructor creates explicit empty evidence, so engines that do not emit
artifacts remain valid without returning `null`.

### Artifact Abstraction

`ExecutionArtifact` describes an artifact using a UUID, provider-neutral type, display name,
content type, byte size, immutable metadata, and `ExecutionArtifactReference`. Supported types are
`LOG`, `SCREENSHOT`, `VIDEO`, `TRACE`, `REPORT`, `ATTACHMENT`, and `METADATA`.

References contain only an absolute URI, storage-provider name, and optional checksum and
compression descriptors. Neither artifacts nor references contain byte arrays, streams, file
paths, provider clients, credentials, or upload behavior. The existing JPA
`ExecutionArtifact` entity and repository are deliberately not used by this collection layer.

### Collection, Validation, and Normalization

`ExecutionEvidenceCollector` exposes only `collect`, `validate`, and `normalize`.
`ExecutionEvidenceCollectorImpl` is stateless and:

- reads evidence already returned by the provider-neutral engine result;
- sorts artifacts deterministically by artifact UUID;
- regenerates `artifactCount` from the normalized artifact list;
- preserves provider-reported warning/error counts and duration;
- validates execution/runner identity and result-duration consistency; and
- returns a new immutable evidence value without performing storage.

`ExecutionEvidenceValidator` fails closed for null evidence or artifacts, duplicate artifact IDs,
identity mismatch, invalid/credential-bearing or relative reference URIs, and summary/artifact
count mismatch. Record constructors reject missing mandatory values, null types/references,
negative sizes/counts/durations, blank metadata keys, and null metadata values. All incoming
collections are defensively copied into unmodifiable collections.

The lifecycle validates and normalizes evidence after validating the engine result and before the
existing fenced completion. Invalid evidence is normalized to the existing
`INVALID_ENGINE_RESULT` failure classification; provider-specific exceptions remain contained.
No storage or database transaction surrounds collection.

## Architectural Decisions

### Preserve the existing durable lifecycle

`STARTING`, `EXECUTING`, `FINALIZING`, and cleanup are runner-local phases. They do not create a
second persisted lifecycle. Successful completion maps to `PASSED`, completed assertion failures
to `FAILED`, operational failures and timeout to `ERROR`, and cooperative cancellation to
`CANCELLED`.

### Build an immutable runtime context

The context loader validates and deep-copies admitted snapshots, ordered selections, Project
identity, deterministic variables, engine identity, runner metadata, ownership controls,
deadline, cancellation, and evidence policy. Mutable catalog data cannot redefine admitted work.
Resolved secrets remain in a separate invocation-scoped sensitive view and are never persisted.

### Use a provider-neutral engine contract

Every engine declares a stable ID, implementation version, compatible contract versions, and
capabilities. Exactly one provider is selected by exact engine ID and contract compatibility.
Engines validate and execute a context, receive cancellation, emit normalized results/evidence,
and clean up. They cannot access platform repositories, ownership credentials, arbitrary secrets,
or authoritative lifecycle transitions.

### Keep orchestration runner-mediated

The orchestrator sequences context preparation, provider selection, fenced start, execution,
lease supervision, cancellation, normalization, fenced finalization, post-commit events, and
cleanup. It owns failure precedence and contains no Playwright-specific path.

### Preserve lease ownership and short transactions

`execution_lease` remains the only ownership record. Start and terminal writes validate the full
fencing tuple and current execution state in short transactions. External secret, workspace,
engine, evidence, and event work occurs outside database transactions.

The current AS-019 heartbeat is `CLAIMED`-only. AS-022C must deliberately reconcile renewal for
`RUNNING` and cooperative `CANCEL_REQUESTED` work while preserving PostgreSQL time, token,
generation, version, and lock-order safeguards.

### Normalize evidence behind ports

Logs, screenshots, stdout/stderr, console output, attachments, native reports, and metadata flow
through a bounded orchestrator-owned sink. Engines do not choose storage paths or write platform
tables. Byte storage, retention, video, and streaming remain deferred.

### Classify but do not retry

Assertion failure is a completed `FAILED` result. Startup, crash, timeout, infrastructure, and
unexpected failures are `ERROR`; cancellation is `CANCELLED`; lost ownership permits no stale
write. Retryability metadata is future policy input only. Persistence/upload retry must never
rerun the engine.

## Key Invariants

- A claim transaction commits before orchestration starts.
- Exactly one current execution lease authorizes work.
- Claim tokens never reach engines, logs, events, or evidence metadata.
- A stale runner cannot start, renew, or finalize.
- Engine ID and contract compatibility select a provider deterministically.
- Snapshot validation fails closed; mutable catalog state is not a fallback.
- Secret values are runtime-only and least-scoped.
- External work never holds scheduling locks or long database transactions.
- Engines emit facts; only the platform assigns authoritative outcomes.
- Cancellation and timeout cannot be overwritten by a late success callback.
- Cleanup is bounded and idempotent.
- No automatic execution retry occurs.

## Risks

- Extending lease renewal beyond `CLAIMED` without one reviewed lock order could introduce
  heartbeat, cancellation, and finalization races.
- Runner loss after `RUNNING` has no approved resume/retry/recovery policy yet.
- An in-process provider can affect runner stability until stronger isolation is approved.
- Weak provider output bounds could exhaust disk or memory.
- Secret redaction cannot compensate for giving an engine unnecessary secrets.
- Provider ambiguity or contract drift could make admitted work unexecutable.
- Evidence storage and event delivery failures need explicit policy so they do not silently
  rewrite valid test results.
- Late engine callbacks must be fenced after timeout, cancellation, or ownership loss.

## Deferred Work

- Distributed execution, parallel execution, and remote execution clusters.
- Artifact/evidence storage implementation and retention.
- Video recording and live streaming.
- Plugin marketplace, dynamic installation, signing, trust, and isolation.
- Execution retries, attempts, resume, and orphaned-running recovery.
- Execution history UI.
- Source workspace and checkout implementation.
- Concrete secret provider and authorization enforcement.
- Durable event delivery/outbox.
- Final engine-contract code shape and result schemas.

## Implementation Safeguards

- Do not add provider-specific branching to the orchestrator.
- Do not pass repositories or lease credentials into an engine.
- Do not add a second ownership or business lifecycle model.
- Do not persist resolved secrets or raw sensitive context.
- Do not consult mutable suite/environment data as a snapshot fallback.
- Do not execute engines in a claim, heartbeat, REST, or persistence transaction.
- Do not finalize after any ownership fence fails.
- Do not map timeout or engine crash to assertion `FAILED`.
- Do not treat local phase telemetry as a resume checkpoint.
- Do not implement retries without an approved attempt/history design.
- Do not select providers by classpath order.
- Do not begin a later phase before the current review gate is approved.
