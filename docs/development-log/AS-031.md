## AS-031A - Architecture, Requirements, and Security Contract

AS-031A is documentation-only. Repository and roadmap discovery from the preceding review was not
restarted. The repository authorities and existing Playwright, REST Assured, and Karate patterns
were re-established before recording the Selenium contract.

### Architecture decisions

1. Canonical identity is `selenium-java`/`1.0.0`; manifest schema is `1.0`.
2. Selenium Java 4.46.0 is the dependency baseline for AS-031C verification and remains
   provider-local.
3. “Selenium Java” identifies the provider library, not repository Java execution.
4. V1 uses a strict passive declarative JSON manifest; Java/JUnit/TestNG/build/shell execution is
   excluded.
5. The statically trusted provider remains in-process only as an adapter. Selenium, driver, browser,
   profile, and network activity run in a disposable digest-pinned Linux worker container.
6. V1 supports one image-qualified Chrome/Chromium family plus compatible ChromeDriver.
7. Selenium Manager, WebDriverManager, PATH discovery, runtime downloads, Grid, remote WebDriver,
   cloud providers, raw capabilities, flags, proxies, certificate bypass, and extensions are not
   authorities.
8. One private network, browser egress gateway, worker, loopback/restricted-origin driver service,
   session, process group, profile, and window are owned per execution; execution is sequential.
9. The worker has no direct egress. All browser traffic is forced through a gateway that admits only
   the normalized target origin and denies control-plane/private infrastructure and DNS rebinding.
10. Secrets resolve lazily only for sensitive fill through existing `ExecutionSecretAccess`.
11. One mandatory safe JSON report publishes through AS-028 after provider admission and has no
    disable switch. Page source, HAR, downloads, and general screenshots are prohibited/deferred.
12. AS-031B adds and independently verifies the provider-neutral execution-control prerequisite
    before AS-031C or any Selenium dependency/provider implementation. It exposes deadline/remaining
    time/cancellation/teardown without Selenium types. Other platform authorities remain unchanged.
13. Runtime absence requires process and container/network identities, not `quit()` or name-based
    killing. Unproved absence is `ERROR`; `RunnerManagementService` performs a version-safe
    transition to `RunnerStatus.DISABLED`, which existing active-only eligibility uses to deny work.

### Playwright comparison

AS-031 reuses the conceptual declarative manifest, strict configuration, same-origin navigation,
ordered actions, operator-owned executable provisioning, non-persistent state, sanitized outcomes,
and reverse cleanup precedent. Selenium-specific implementation owns driver-service lifecycle,
worker-local WebDriver endpoint, browser/driver compatibility, explicit waits, contained process-
group cleanup, and runtime absence proof. No Playwright implementation class becomes a dependency.

### REST Assured and Karate lessons

REST Assured confirms provider-local dependencies, passive manifests, strict target authority,
lazy secrets, sanitized reporting, and static assembly. Karate confirms that source authority
determines containment strength, test-only reachability must not weaken production, resource
ownership must be bounded, cleanup must verify absence, and native reports/diagnostics cannot cross
the provider-neutral boundary without a safe model. Karate's isolation principles are reused, but
the browser gateway independently covers subresources, CONNECT, WebSockets, service workers, DNS,
and background traffic rather than copying the API gateway unchanged.

### Security review

Threats and verification strategies are recorded in ADR-021 for arbitrary code, filesystem and
environment access, executable acquisition, driver endpoint exposure, SSRF/navigation, browser
subresources, secret/artifact leakage, malicious capabilities, downloads, persistent browser state,
resource exhaustion, runaway processes, diagnostics, and cleanup failure.

Independent review found two blocking architecture gaps: no provider-visible deadline/cancellation
capability in the current SDK, and no enforceable defense against a permitted page reaching local/
private/control-plane services. It also found underspecified process ownership and a contradiction
between mandatory reporting and `captureFailureReport`.

The remediation defines a separately reviewed provider-neutral execution-control/supervision
prerequisite, a digest-pinned disposable worker with no direct egress, a browser-specific forced
gateway, runtime-identity absence evidence with protective runner disable, and one unconditional
required report.
No SDK/runtime implementation is part of AS-031A.

Final independent-review remediation maps the earlier quarantine concept to the existing runner lifecycle owner and
`DISABLED` status with locked expected-version concurrency, explicit operator recovery, and alerting
when disable fails. It makes the execution network default-deny for IPv4, IPv6, UDP, QUIC/HTTP3,
WebRTC/STUN/TURN, alternate DNS, direct IP, proxy bypass, external debugging, host networking, and
unsupported protocols. It maps required report generation/publication failure to canonical `ERROR`
over every provider outcome, defines one composite supervisor-owned teardown handle, and requires a
compatibility constructor/factory plus bounded production control for existing providers.

## AS-031B - Provider-Neutral Execution Control and Supervision

Implementation adds a JDK-only SDK execution control with an immutable wall deadline, monotonic
non-increasing remaining time, cancellation observation, explicit bounded identity, and one
provider-neutral teardown registration. Existing four- and five-argument request constructors use
an explicitly unavailable compatibility control; canonical orchestration always supplies the
bounded platform control derived from admitted execution timeout.

Provider invocation now runs on an execution-scoped virtual thread under platform supervision.
The supervisor polls cancellation every 10 ms, gives deadline priority over cancellation and
provider completion, interrupts the provider only as a secondary mechanism, invokes registered
teardown independently with a two-second platform-owned bound, and rejects late completion.
Accepted cancellation completes only from persistent `CANCEL_REQUESTED` through existing
`Execution.markCancelled()` semantics. The exact version observed with `CANCEL_REQUESTED` is retained
as platform orchestration metadata and becomes the locked completion request's execution-version
fence; runner, claim-token, lease-generation, lease-version, and lease-expiry fencing remain intact.
Termination waits within one platform-owned two-second registration-and-teardown window. A teardown
registered during that window is supervised exactly once, registration after closure is rejected,
and missing registration returns boundedly. Teardown timeout, execution failure, and supervisor
interruption have distinct sanitized operational classifications, with interruption restored.
Deterministic tests cover an interruption-ignoring provider, late result/exception rejection,
deadline/cancellation priority, late teardown success/failure/timeout, missing and post-close
registration, and exact-versus-stale cancellation versions. Sanitized orchestration failures now
carry optional immutable platform-owned cancellation-observation metadata. The metadata-bearing
exception constructor is private, ordinary callers retain only public constructors without a
cancellation version, and package-internal enrichment is invoked by orchestration only after
`PlatformExecutionControl` reports the repository observation. The public orchestration result
likewise contains only provider-neutral engine outcome data. Exact cancellation version metadata
is carried separately in a package-internal platform outcome created by the final production
orchestrator; the coordinator's public alternate-orchestrator path cannot create that outcome and
fails closed on an untrusted cancellation result. Positive cancellation observations, their probe,
the repository probe, the probe-injecting orchestrator constructor, and the concrete trusted
coordinator constructor are package-internal. Spring creates the repository-backed orchestrator
and trusted coordinator through package-local bean factories in `PlatformExecutionConfiguration`,
so arbitrary backend application code cannot assemble the trusted path while package-local tests
retain deterministic injection. Teardown exception,
teardown timeout, artifact finalization, and mandatory cleanup failures after cancellation use the
exact observed version for durable `ERROR` completion. The locked validator still rejects that
observation after an unrelated advance to N+1; no reload, reconstruction, retry, or version-fence
bypass exists. A PostgreSQL-backed integration test drives the real coordinator, orchestrator,
transactional completion service, locked execution/lease repositories, and ownership validator for
those four cancellation/error cases, stale N-to-N+1 rejection, and the ordinary no-cancellation
error path, asserting the final durable state, version, and sanitized result. No existing provider
was required to poll the new
control, and no Selenium or later-story implementation was introduced.

### AS-031D1 resource identity, worker lifecycle, and bounded IPC

AS-031D1 is implemented locally as an intentionally package-local foundation. The new JDK-only
`selenium-worker-runtime` reactor module supplies a non-root, digest-pinned Java 21 image contract,
an execution-derived ephemeral workspace, exact JVM ownership, and a 256-byte length-prefixed
HELLO/READY/SHUTDOWN/BYE protocol. It contains no browser, driver, Selenium, network client,
studio-api, Spring, or runtime-download dependency.

The Selenium plugin now separates immutable Docker identity, digest-only command construction,
bounded argv-only Docker CLI execution, lifecycle limits, an execution-owned resource aggregate,
and sanitized absence reporting. Exactly one composite teardown is registered before `docker
create`; acquisition is atomic, cleanup is one-shot/race-safe and reverse ordered, and removal is
fail-closed unless the inspected immutable container ID and execution UUID label exactly match.
Container absence is authoritative for its JVM, ephemeral profile/runtime/tmpfs, and IPC state.

This D1 foundation uses only Docker `--network none`; it makes no AS-031D2 network-security claim.
AS-031D2 through D5 and AS-031E have not started. `SeleniumEnginePlugin.execute()` remains inert
with `SELENIUM_RUNTIME_NOT_AVAILABLE`; there is no provider/Spring/backend activation.

stopped; unresolved helpers make `closed()` false and therefore preserve unsafe cleanup semantics.
