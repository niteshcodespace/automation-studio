## Approved-for-Review Architecture

### Identity

- `Runner.id` is a server-generated immutable UUID.
- `runnerKey` is a canonical, globally unique, immutable logical identity.
- AS-019's string `runnerId` remains backward compatible and maps to `runnerKey`.
- Neither identifier is trusted authentication.
- Active re-registration updates the same row; disabled/deregistered registration is rejected.
- Deregistered keys remain reserved.

### Metadata and Capabilities

- Required host/agent metadata and maximum concurrency are stored on the runner resource.
- Re-registration atomically replaces mutable metadata, capabilities, and labels.
- Heartbeat does not alter advertised metadata.
- Capabilities and labels use bounded JSONB with GIN indexes; the requirements define exact
  document size, depth, and entry limits.
- Engine IDs are strings; no engine enum or AS-026 implementation is introduced.

### Lifecycle, Health, and Availability

- Persisted status is `ACTIVE`, `DISABLED`, or `DEREGISTERED`.
- Health is calculated as `ONLINE`, `STALE`, or `OFFLINE` from database time and configured
  thresholds, defaulting to one minute online and five minutes offline.
- No scheduler writes offline status.
- Disabled runners may remain online but are unavailable.
- Dispatch eligibility is a registry-level calculation, not capacity reservation or scheduling.

### Persistence and Concurrency

- `runner` stores identity, metadata, lifecycle, capability data, and management version.
- `runner_runtime` stores current liveness, heartbeat count, and runtime-local version.
- The separation prevents heartbeat traffic from invalidating management `If-Match` versions.
- Management mutations use optimistic locking.
- Heartbeats lock `runner -> runner_runtime`, then obtain PostgreSQL `clock_timestamp()`.
- Runner/runtime creation and re-registration are transactional.

### REST Proposal

Proposed AS-020 routes:

```http
POST  /api/v1/runners
POST  /api/v1/runners/{runnerId}/heartbeats
GET   /api/v1/runners
GET   /api/v1/runners/{runnerId}
PATCH /api/v1/runners/{runnerId}/status
```

Existing AS-019 routes remain unchanged:

```http
POST /api/v1/runners/claim
POST /api/v1/runners/heartbeats
POST /api/v1/runners/reclaim
```

Registration returns 201 for creation and 200 for active re-registration. List uses Spring Data
pagination and an allow-listed stable sort. Status changes require `If-Match`. Errors use the
existing structured and sanitized response.

## AS-019 Boundary

Runner-level heartbeat proves that a registered process is alive. Execution-lease heartbeat
renews ownership of one claimed execution. Neither operation substitutes for the other.

AS-020A makes no change to:

- AS-019 request or response DTOs;
- `/api/v1/runners/claim`, `/api/v1/runners/heartbeats`, or
  `/api/v1/runners/reclaim`;
- `execution_lease.runner_id`;
- claim tokens;
- lease generations or versions;
- execution lifecycle or versioning; or
- expired-lease reclaim.

Registry validation of AS-019 `runnerId` is deferred to a reviewed implementation phase and must
preserve the current string contract.

## AS-020B Implementation

AS-020B adds the forward-only migration:

```text
V12__create_runner_registry.sql
```

The migration creates:

- `runner`, containing the durable UUID identity, canonical unique runner key, registration
  metadata, lifecycle status, JSONB capabilities and labels, management version, and audit
  timestamps; and
- `runner_runtime`, containing the shared runner primary/foreign key, authoritative last-seen
  timestamp, heartbeat count, runtime-local version, and audit timestamps.

Database constraints enforce:

- canonical lowercase runner-key syntax and uniqueness;
- nonblank required identity and host metadata;
- `max_concurrency` between 1 and 1000;
- lifecycle status limited to `ACTIVE`, `DISABLED`, and `DEREGISTERED`;
- nonnegative management/runtime versions and heartbeat count;
- JSONB object roots and a 64 KiB normalized JSONB text bound for capabilities and labels;
- registration and audit timestamp ordering; and
- one runtime row per runner with restrictive deletion.

Indexes support:

- unique runner-key lookup;
- status/name/id registry listing;
- GIN containment queries over capabilities and labels; and
- last-seen/runtime-id health scans.

V12 deliberately adds no foreign key from `execution_lease.runner_id` to the registry and performs
no runner backfill. An upgrade test preserves a representative AS-019 execution lease whose
string runner ID has no registry row.

### JSONB Validation Boundary

PostgreSQL enforces non-null JSONB, object roots, normalized textual size, and GIN indexing.
AS-020C/AS-020D validation must enforce request-level UTF-8 size, maximum nesting depth, aggregate
capability member/element count, label count, label key/value rules, duplicate input keys, and
the string engine-ID/version contract. Those rules are not implemented as procedural database
validation in AS-020B.

## AS-020C Implementation

AS-020C adds the Java persistence model for V12:

- `RunnerStatus` with exactly `ACTIVE`, `DISABLED`, and `DEREGISTERED`;
- `Runner`, mapping all 17 `runner` columns; and
- `RunnerRuntime`, mapping all six `runner_runtime` columns.

Both entities use `OffsetDateTime`, database-sourced creation/update timestamps, and independent
JPA optimistic versions. `Runner` has no runtime association, health, availability, execution
lease, or delete cascade.

### JSONB Mapping

`Runner.capabilities` and `Runner.labels` use the repository's existing Hibernate
`@JdbcTypeCode(SqlTypes.JSON)` and `Map<String, Object>` approach with PostgreSQL JSONB columns.
Unlike the existing shallow-copy mappings, the runner entity recursively copies nested maps and
lists on input and output so callers cannot mutate its managed JSON state through shared nested
references.

Request-level shape, depth, member count, label semantics, engine-ID/version semantics, duplicate
key detection, sensitive-value rules, and original UTF-8 request size remain deferred to the
registration/capability service phases.

### Runner Runtime Identity

`RunnerRuntime` maps `runner_id` as a scalar UUID primary key rather than using `@MapsId`.
The V12 foreign key remains the database integrity boundary. This keeps runtime retrieval and
updates independent, prevents accidental runner loading or dirtying during future heartbeat
writes, and makes the absence of an eager bidirectional graph explicit.

### Repository Surface and Lock Ordering

`RunnerRepository` provides:

- inherited UUID CRUD;
- `findByRunnerKey`;
- `existsByRunnerKey`;
- paged `findByStatus`;
- `findByRunnerKeyForUpdate`; and
- `findByIdForUpdate`.

`RunnerRuntimeRepository` provides:

- inherited UUID CRUD;
- `findByRunnerId`;
- `existsByRunnerId`; and
- `findByRunnerIdForUpdate`.

All `ForUpdate` methods use `PESSIMISTIC_WRITE` and must be called inside a transaction. Future
heartbeat transactions must acquire `Runner` through its lock query before calling the runtime
lock query. No repository operation combines them in the reverse order.

Capability containment, label containment, text search, health calculation, and availability
queries remain deferred to AS-020G.

## AS-020D Implementation

AS-020D adds the service-only runner registration workflow:

- `RegisterRunnerCommand`, containing registration metadata without REST or Bean Validation
  annotations;
- `RunnerRegistrationService`, exposing registration and UUID/key retrieval; and
- `RunnerRegistrationServiceImpl`, providing transactional registration, re-registration,
  lifecycle enforcement, input validation, database-time initialization, and persistence conflict
  translation.

`RunnerAlreadyDeregisteredException` is the only new exception. It extends the existing
`ResourceConflictException` so a later REST phase can preserve the shared 409 mapping without
adding a parallel exception hierarchy.

### Registration and Re-registration

Registration canonicalizes a trimmed runner key to lowercase and validates database-backed scalar
bounds. Capabilities and labels must be non-null maps. AS-020D deliberately does not add JSON
depth, cardinality, semantic, sensitive-value, engine-compatibility, or serialized request size
validation.

A new key creates one `ACTIVE` `Runner` and one `RunnerRuntime` in the same transaction. One
PostgreSQL `clock_timestamp()` value initializes `registeredAt`, `lastRegisteredAt`, and
`lastSeenAt`; heartbeat count and both optimistic versions begin at zero.

Re-registration preserves the runner UUID, canonical key, original registration time, creation
time, persisted status, and runtime row. It replaces only mutable runner metadata and advances
`lastRegisteredAt` and the runner management version. It locks and verifies the runtime row but
does not modify `lastSeenAt`, heartbeat count, runtime timestamps, or runtime version.

The AS-020D phase brief explicitly allows both `ACTIVE` and `DISABLED` re-registration while
preserving status. This differs from the earlier AS-020A requirements/ADR text that rejects
disabled re-registration. The phase brief is treated as the controlling implementation contract;
the requirements and ADR should be reconciled at the next documentation review. `DEREGISTERED`
remains terminal and re-registration raises `RunnerAlreadyDeregisteredException`.

### Concurrency and Transactions

`register` is one Spring transaction. It first acquires a transaction-scoped PostgreSQL advisory
lock derived from the canonical runner key. This closes the missing-row gap for concurrent first
registrations without adding a lock table. It then uses the repository's
`PESSIMISTIC_WRITE` runner-key query and, for re-registration, the runtime
`PESSIMISTIC_WRITE` query.

The row-lock order remains:

```text
runner -> runner_runtime
```

New persistence is flushed in the same order. Key-scoped serialization ensures concurrent first
registrations converge on one runner UUID and one runtime row; later callers follow the
re-registration path. Database constraint and optimistic-lock failures are translated to the
existing sanitized `ResourceConflictException`. Any runtime persistence failure rolls back the
runner insert.

The concurrency test exposed that Hibernate's database `@UpdateTimestamp` expression uses
PostgreSQL transaction-start time. A transaction that began before waiting for the registration
lock could therefore attempt an `updated_at` earlier than the existing `created_at`. `Runner`
now uses Hibernate-generated `clock_timestamp()` for insert/update audit time, preserving V12's
audit-order constraint for queued transactions without a migration.

## AS-020E Implementation

AS-020E adds runner-level liveness recording and read-time health evaluation:

- `RunnerHealth` with exactly `ONLINE`, `STALE`, and `OFFLINE`;
- `RecordRunnerHeartbeatCommand`, containing only the canonical logical runner key;
- immutable `RunnerHeartbeatResult` and `RunnerHealthResult` service values;
- `RunnerHeartbeatService` and `RunnerHeartbeatServiceImpl`; and
- validated `RunnerHealthProperties` registered by `RunnerHealthConfiguration`.

No caller observation timestamp is accepted. PostgreSQL remains the sole authority for persisted
heartbeat time.

### Heartbeat Workflow and Runtime Mutation

`recordHeartbeat` canonicalizes the runner key, locks the runner, validates lifecycle, locks its
required runtime row, obtains `clock_timestamp()`, calls the controlled
`RunnerRuntime.recordHeartbeat` mutation, flushes, and commits atomically.

The mutation rejects null or backward timestamps, increments heartbeat count exactly once with
overflow detection, and relies on the runtime-local `@Version` for each accepted update. It does
not expose setters or modify runner identity, metadata, lifecycle, audit fields, or management
version. A missing runtime is an invariant failure and is never silently recreated.

`RunnerRuntime.updatedAt` now uses the same generated PostgreSQL `clock_timestamp()` expression as
`Runner`. This prevents serialized heartbeat transactions from writing transaction-start audit
times and keeps runtime audit time monotonic with the accepted database heartbeat time without a
migration.

### Lifecycle and Locking

The requirements and ADR consistently allow `ACTIVE` and `DISABLED` runners to report liveness.
`DISABLED` heartbeat therefore updates runtime state without reactivation; availability remains
false because lifecycle and health are separate. `DEREGISTERED` is terminal and heartbeat is
rejected with the existing sanitized `ResourceConflictException`.

The AS-020E brief's safe-behavior recommendation to reject disabled heartbeat applies only if the
documentation is inconsistent. No heartbeat discrepancy exists, so the approved requirements and
ADR control.

Every write uses this pessimistic row-lock order:

```text
runner -> runner_runtime
```

Database time is obtained only after both locks. Concurrent heartbeats serialize, each succeeds
once, and later transactions cannot commit an older `lastSeenAt`. Registration's advisory key
lock is not used for already registered heartbeat updates.

### Derived Health and Configuration

Health is calculated from runtime state without persistence:

```text
age <= online threshold                    -> ONLINE
online threshold < age <= offline threshold -> STALE
age > offline threshold                    -> OFFLINE
```

A future `lastSeenAt` is clamped to zero age. Results always return persisted lifecycle status and
derived health separately, including for disabled and deregistered runners.

Configuration uses the documented prefix and defaults:

```properties
automation-studio.runners.health.online-threshold=PT1M
automation-studio.runners.health.offline-threshold=PT5M
```

Both durations must be positive, and the offline threshold must be greater than the online
threshold. Invalid values fail configuration binding during startup.
