## Terminology and version decisions

Canonical identity terms are `engineId` and `implementationVersion`. Both are opaque,
case-sensitive, exact strings. Display name, alias, bean name, registration order, version range,
case folding, trimming, fallback, and implicit defaults are never resolution inputs.

A separate plugin-contract version is deferred. Current compatibility uses the shared Java
contract plus exact implementation version. This reconciles historical conceptual contract-version
language without adding a field or negotiation policy unsupported by code.

## Compatibility decisions

Prepared `EngineExecutionRequest` is the canonical invocation direction. The legacy
`execute(ExecutionContext)` method remains temporarily for Builtin/default-adapter source
compatibility and is not a second orchestration path. Deprecated descriptor/constant aliases also
remain temporary read-only compatibility surfaces. No removal deadline is approved in AS-026A.

Repository-internal contract verification belongs to AS-026. A reusable SDK, external fixtures,
third-party harness, sample plugin, packaging, and developer distribution belong to AS-027.

## Workspace, source and secret boundaries

AS-023 continues to own physical workspace creation/release/deletion and exact source
materialization. Engines receive immutable preparation and narrow workspace access only, close
their access handles, and cannot choose/delete the physical workspace or alter source identity.

AS-025 continues to own execution-scoped secret provider selection, lazy resolution, admitted-name
binding, value lifetime, and scope cleanup. Resolved values remain outside descriptors, registry,
context, normal variables, persistence, results, logs, and errors. AS-026 introduces no provider or
secret authority.

## Result, cleanup and artifact decisions

The current `EngineExecutionResult` is provider-neutral and bounded to identity, prepared source/
workspace, normalized state, and timing. AS-026 may verify consistency and safe failure/cleanup
behavior but does not standardize durable artifacts.

Engines close invocation resources in reverse order. Orchestration retains invocation order,
secret-scope cleanup, and physical workspace release. Lifecycle services retain fenced durable
completion. ADR-014/ADR-015 failure precedence remains authoritative.

Durable artifact metadata, categories, publication, integrity, retention, and discovery remain
AS-028. Temporary engine/workspace files are not durable artifact references.

## AS-026C - Registry Resolution and Compatibility Hardening

### Repository baseline

Implementation began from clean synchronized local `main` at
`96e7fb5db84e6edbf98540d775cc23b672ac8c62`, containing the approved AS-026A documentation and
AS-026B canonical descriptor contract.

### Implementation

AS-026C preserves the existing registry interface and static Spring registration model. It:

- validates and canonically sorts all engine supports before publishing registry state;
- retains immutable insertion-ordered maps and the immutable deterministic descriptor list;
- checks that each engine returns a stable descriptor during registration and lookup;
- maps null, throwing, or inconsistent descriptors to a fixed safe invalid-descriptor failure;
- distinguishes unsupported implementation version and ambiguous name-only resolution with narrow
  exception subclasses that preserve the existing compatibility-exception hierarchy; and
- keeps duplicate and unknown-engine failures separate without exposing requested identities,
  implementation classes, bean names, configuration, paths, or secrets.

No engine, orchestration, execution lifecycle, request/result, source/preparation, workspace,
secret, cleanup, scheduling, persistence, Flyway, REST, browser, or manifest behavior changed.
