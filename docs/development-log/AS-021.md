# AS-021 - Runner Scheduling

## Feature

Runner-aware, scheduler-assisted pull that selects compatible queued executions and enforces
registered runner capacity while retaining the AS-019 execution lease as the sole ownership
model.

## Objectives

- Validate the pulling runner against AS-020 identity, lifecycle, and calculated health.
- Select the oldest compatible AS-018/AS-019 execution using immutable admission snapshots.
- Enforce `maxConcurrency` from current unexpired execution leases.
- Preserve AS-019 claiming, fencing, heartbeat, reclaim, and rollback behavior.
- Coordinate scheduling with PostgreSQL and a runner-first lock order.
- Avoid a second assignment, reservation, queue, or ownership model.

## Architectural Decisions

### Scheduler-Assisted Pull

The runner continues to initiate `POST /api/v1/runners/claim`. The server validates the runner
and selects the oldest compatible work. There is no push dispatcher or runner inbox.

### Existing Lease Ownership

The AS-019 `execution_lease` remains the only current ownership record. A successful scheduling
decision still atomically performs `PENDING -> CLAIMED` and creates that lease. No assignment or
reservation table is introduced.

### Runner Eligibility

Scheduling requires a registered `ACTIVE`, `ONLINE` runner with a required runtime row and at
least one available slot. The existing claim `runnerId` maps to the immutable AS-020 `runnerKey`.

### Compatibility

The immutable suite snapshot's nonblank `engineId` must exactly match a key in
`runner.capabilities.engines`. Explicit admitted mandatory capabilities and label key/value pairs
also match exactly. Mutable suite state and arbitrary configuration are not inferred scheduling
requirements. Engine version negotiation is deferred.

### Lease-Derived Capacity

Capacity counts unexpired leases for the runner key whose executions are `CLAIMED`, `RUNNING`, or
`CANCEL_REQUESTED`. `lease_expires_at == databaseNow` is expired and does not consume capacity.
No available-slot counter is persisted.

### PostgreSQL Coordination

The lock order is:

```text
runner -> runner_runtime -> execution -> execution_lease
```

Same-runner requests serialize on the runner row. PostgreSQL filters compatible candidates and
uses `FOR UPDATE SKIP LOCKED` with `requested_at ASC, id ASC`. One database time controls health
and lease-expiry decisions.

### REST Boundary

The existing claim endpoint, lease duration, and response are retained. Success returns 200;
empty compatible work or exhausted capacity returns 204; malformed input returns 400; an unknown
runner returns 404; and an existing ineligible runner returns 409 through structured errors.

Request-ID idempotency is deliberately deferred. The AS-019 claim token is not a substitute.

## Risks

- Incorrect lock ordering could deadlock runner management, scheduling, and execution ownership
  operations.
- A capacity query that differs from lease expiry or lifecycle semantics could overbook or
  underutilize runners.
- JSONB compatibility predicates could become inefficient without PostgreSQL-focused query
  evidence.
- Snapshot shape drift could make older executions unschedulable; malformed or absent mandatory
  requirements must fail closed without blocking compatible later work.
- `SKIP LOCKED` may temporarily bypass the oldest compatible locked row.
- Caller-provided runner identity and capability data remain untrusted until authentication.
- A lost successful response may lead a retry to claim more work while capacity remains because
  request-ID replay protection is deferred.

## Implementation Safeguards

- Do not add a second queue, assignment, reservation, lease, or ownership token.
- Do not let the runner select an execution ID.
- Do not use mutable Automation Suite state for admitted execution compatibility.
- Do not infer scheduling constraints from free-form configuration.
- Do not use application or client time for health, lease expiry, or capacity.
- Do not persist a capacity counter in AS-021.
- Do not count expired or terminal ownership as active capacity.
- Do not reverse the runner-first lock order.
- Do not expose claim tokens or snapshots in logs, errors, or metrics.
- Do not alter AS-019 heartbeat or reclaim without a proven shared defect and explicit review.
- Do not use arbitrary sleeps in concurrency tests.
- Do not begin a later phase before the current review gate is approved.

## AS-021B Implementation

### Persistence Design

The existing execution snapshots are sufficient for the approved persistence boundary:

- `suite_snapshot.engineId` is the immutable engine requirement used by later compatibility
  selection.
- `request_snapshot` is the future source of explicitly admitted mandatory constraints.
- `environment_snapshot` remains admission-time execution context and is not duplicated.

V13 adds no column, scheduling table, assignment table, history table, or mutable scheduling
metadata. It enforces the existing snapshot immutability contract with a PostgreSQL trigger and
adds a partial expression index:

```text
(suite_snapshot ->> 'engineId', requested_at, id)
WHERE status = 'PENDING'
  AND engineId is nonblank
```

The index supports the approved exact-engine compatible FIFO query shape without implementing
that query in AS-021B. Historical null or incomplete snapshots remain valid and unchanged; later
scheduling fails them closed.

### JPA and Repository Reconciliation

No JPA model change is required. `Execution` already maps the three JSONB snapshots and returns
defensive copies. No repository change is required because scheduling queries belong to AS-021C.
The full regression proves existing Hibernate lifecycle updates remain compatible with the
database trigger when snapshot values are unchanged.

## AS-021C Implementation

### Scheduling Domain

AS-021C adds immutable scheduling values:

- `SchedulingRequirements` for the required engine, capability JSON, and label pairs;
- `RunnerCapabilities` for the runner's deeply copied advertised capability and label documents;
- `CompatibilityResult` with engine, capability, and label mismatch outcomes;
- `RunnerCompatibilityEvaluator` for exact engine/label matching and recursive JSON containment;
  and
- `SchedulingCandidate` for a read-only execution candidate projection.

`SchedulingRequirementsParser` validates the complete AS-018 environment, suite, and request
snapshot shapes. Snapshot environment/suite IDs, selection mode, requester, and request timestamp
must match their relational execution fields. Missing, malformed, or inconsistent snapshots fail
closed and are never repaired.

Optional admitted constraints are read only from:

```text
request_snapshot.requiredCapabilities
request_snapshot.requiredLabels
```

Absence means no additional constraint. A present capability value must be an object; required
labels must be a string-to-string object. `suite_snapshot.engineId` remains mandatory.

### Candidate Repository

`SchedulingCandidateRepository` and `PostgreSqlSchedulingCandidateRepository` provide one
read-only operation that returns at most the oldest compatible candidate.

PostgreSQL:

- restricts status to `PENDING`;
- excludes any execution already carrying an `execution_lease`;
- validates required snapshot structure and relational consistency;
- matches the engine against the runner's registered engine keys;
- applies JSONB containment for mandatory capabilities and labels;
- fails closed for historical incomplete snapshots;
- orders by `requested_at ASC, id ASC`; and
- uses the V13 `idx_execution_pending_engine_queue` index for compatible FIFO access.

The query contains no `FOR UPDATE` or `SKIP LOCKED`. It creates no lease and changes no execution.
Lock acquisition and transactional ownership remain assigned to later phases.

### AS-021C Tests

Domain tests cover compatible and incompatible engines, missing/malformed engine requirements,
malformed/inconsistent snapshots, recursive capability matching and mismatch, label matching and
mismatch, and explicit compatibility results.
