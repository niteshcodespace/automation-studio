# AS-023 - Runner Workspace and Source Preparation

## Epic Objective

Provide immutable source identity, isolated runner-local workspaces, provider-neutral source
materialization, exact-revision verification, and bounded cleanup so real source-based engines can
execute without acquiring persistence, ownership, or arbitrary host-path authority.

## AS-023B Implementation

### Persistence

Flyway V15 adds:

- `project.source_type`, `project.source_repository`, and `project.source_revision`;
- `test_suite.source_location`; and
- `execution.source_snapshot` JSONB.

Project source values are nullable only as one complete configuration. V15 constrains the initial
type to `GIT_HTTPS` and the revision to lowercase 40-hex SHA-1. Suite paths have deterministic
portable structural checks. Execution source snapshots must be JSON objects and are covered by
the existing immutable-snapshot trigger.

V14 and earlier rows migrate with all new fields null. No repository, revision, workspace path,
credential, or other source identity is fabricated.

### Domain and Validation

- `SourceType` contains only `GIT_HTTPS`.
- `ExecutionSourceReference` is the immutable admitted source value.
- `SourceConfigurationValidator` performs network-free URI, exact revision, and relative-location
  validation and normalization.
- Repository identity requires HTTPS, a host and path, bounded length, no whitespace/control
  characters, and no user-info, query, or fragment.
- SHA-1 requires exactly 40 hexadecimal characters and normalizes to lowercase.
- `sourceLocation` uses forward-slash portable segments, maximum length 500 and depth 20, and
  rejects absolute, drive, UNC, backslash, empty, dot, traversal, and ambiguous paths.

### API Impact

Existing Project create/update/read APIs now accept and return `sourceType`, `sourceRepository`,
and `sourceRevision`. Existing Automation Suite create/update/read APIs accept and return
`sourceLocation`. Execution responses expose `sourceSnapshot`, clearly separated from mutable
Project and Suite fields.

Existing source-absent JSON remains compatible. A Project update that omits all three source
fields preserves its current source configuration.

### Admission and Consistency

Execution admission locks Project then Automation Suite inside the existing short transaction,
validates one coherent source state, and copies it into `source_snapshot`. Project source updates
use the same scoped Project row lock; Suite updates already use their established row lock.
No network, Git, filesystem, or orchestration work occurs.

A Suite with a declared non-BUILTIN `engineId` requires a complete valid source. BUILTIN is
source-independent. A historical Suite whose `engineId` is null remains admissible without a
fabricated source snapshot as the smallest backward-compatible transitional rule.

### AS-023B Test Coverage

- URI, SHA-1, and portable-path validation and normalization.
- Project source create/update/read and credential-bearing URL rejection.
- Suite source-location persistence/API exposure and unsafe-path rejection.
- V15 schema, constraints, V14 migration, legacy null behavior, and immutable trigger.
- Source-based admission failure without configuration.
- Immutable Execution snapshot after Project and Suite changes.
- Execution API reads admitted values rather than mutable catalog values.
- BUILTIN and historical provider-unspecified compatibility.
- Cross-Project Suite rejection.
- Deterministic Project-update/admission serialization proving a complete source version.

AS-023B adds no Git library, resolver, workspace contract, directory, checkout, fetch, engine,

## AS-023C Implementation

AS-023C adds a pure `execution.workspace` contract layer:

- `WorkspaceId` and `WorkspaceProviderId` provide opaque validated identities.
- `WorkspaceDescriptor` binds exactly one immutable workspace identity to one Execution and one
  provider.
- `WorkspaceState` permits only
  `PLANNED -> PREPARING -> READY -> IN_USE -> RELEASING -> RELEASED`.
- `WorkspaceMetadata` records immutable preparation time and the optional admitted source
  reference. A null source preserves source-independent execution compatibility.
- `WorkspacePreparationRequest`/`Result` and `WorkspaceReleaseRequest`/`Result` enforce their
  lifecycle boundaries and correlate provider output with the originating identity, ownership,
  provider, source, and metadata.
- `WorkspaceProvider` is the provider-neutral preparation/release port.

Lifecycle changes return new descriptors. Identity, execution ownership, provider identity, and
prepared metadata cannot change. Metadata is absent before `READY` and required thereafter.
The contract deliberately contains no host locator: no `Path`, `File`, directory string,
filesystem URI, mutable attribute map, JPA type, lease, claim, or transaction type.

AS-023C adds no Spring bean, provider implementation, runtime configuration, persistence,
migration, API, orchestration wiring, filesystem access, temporary directory, source resolver,
Git behavior, cleanup behavior, or Playwright behavior.

## AS-023D Implementation

### Local Provider and Configuration

- `LocalWorkspaceProvider` is the first `WorkspaceProvider` adapter.
- `automation.runner.workspace.root` is bound through `WorkspaceRootProperties`.
- `LocalWorkspaceConfiguration` creates the provider and `WorkspaceManager` only when the root
  property is explicitly present; no default or developer-specific directory is used.
- The root is parsed and normalized at construction, then created and canonicalized lazily on
  the first provider operation.

Root validation rejects blank, relative, dot/traversal, filesystem-root, user-home,
working-directory, linked, and non-directory locations. Its real path must exactly equal the
normalized configured path.

### Workspace Layout and Lifecycle

Each workspace is the immediate root child named by the lowercase canonical workspace UUID:

```text
<root>/<workspace-id>/
    metadata/
    source/
    artifacts/
    temp/
```

Only directories are created. No source, artifact, metadata file, marker, credential, or
temporary content is populated in AS-023D.

`WorkspaceManager` depends only on `WorkspaceProvider`. It coordinates `PLANNED -> PREPARING ->
READY` and `IN_USE -> RELEASING -> RELEASED`, validates provider ownership, returns an already
`RELEASED` descriptor idempotently, and translates adapter failures into a sanitized
`WorkspaceManagementException`.

### Filesystem Safety and Concurrency

- Workspace targets must be normalized immediate children of the canonical root.
- Creation uses exclusive `createDirectory`; an existing target is a duplicate and fails closed.
- Creation failure triggers validated removal of any partial workspace.
- A complete no-follow validation walk precedes deletion.
- Symbolic links and other special entries are rejected rather than traversed.
- Canonical directories must remain inside the canonical workspace.
- A second no-follow deletion walk removes ordinary files and directories only.
- Bounded striped locks serialize operations for the same workspace without an unbounded lock
  registry.
- Concurrent preparation produces one success and one duplicate failure.
- Concurrent and repeated release are idempotent.
- Local paths remain private implementation state and never enter domain contracts or durable
  state.

### AS-023D Test Coverage

- lazy root and deterministic layout creation;
- normal and repeated release;
- duplicate preparation preservation;
- concurrent prepare and release;
- relative, traversal, filesystem-root, and user-home rejection;
- provider ownership and manager lifecycle enforcement;
- manager exception translation;
- conditional Spring configuration; and
- symlink-root and workspace-escape cases, conditionally executed where the host permits creating

## AS-023E Implementation

### Materialization Contracts and Local Path Boundary

- `SourceMaterializer` is the provider-neutral port.
- `SourceMaterializationRequest` combines immutable `WorkspaceId` and the existing
  `ExecutionSourceReference`; no second source model was introduced.
- `SourceMaterializationResult` contains workspace ID, source type, verified revision,
  `MATERIALIZED` state, and materialization time.
- `WorkspaceLocationResolver` and `LocalWorkspaceLocation` exist only in the local infrastructure
  package. `LocalWorkspaceProvider` implements the resolver and reuses its canonical root,
  workspace, and fixed-child validation.
- No AS-023C contract, execution snapshot, API, JPA entity, or database schema contains a path.

### Git Policy and Command Execution

Production supports credential-free HTTPS only and reuses `SourceConfigurationValidator` for the
exact 40-hex SHA-1 and optional relative source location. The test-only
`allow-local-repositories` setting defaults to false and permits local `file:` fixtures without
weakening production policy.

The Git sequence is `init`, `remote add`, exact-SHA shallow `fetch`, detached `checkout`,
`rev-parse --verify HEAD`, and `rev-parse --abbrev-ref HEAD`. Success requires exact revision
equality and the literal detached name `HEAD`.

`ProcessGitCommandRunner`:

- uses `ProcessBuilder` with one argument per value and no shell;
- disables credential helpers, LFS smudge/process filters, and system attributes;
- isolates HOME, XDG/global configuration, templates, and hooks beneath workspace temp;
- disables terminal prompts, credential-manager interaction, askpass, and LFS smudge;
- retains only the minimum process environment needed to locate and run Git;
- drains stdout and stderr concurrently while retaining at most the configured byte limit;
- enforces a maximum-bounded per-command timeout; and
- terminates the process tree, then forcibly terminates after a finite grace period.

Defaults are executable `git`, timeout `PT2M`, and 65,536 bytes per output stream. Timeout is
bounded to `PT10M`; output is bounded to 1,048,576 bytes.

### Repository and Filesystem Safety

- The prepared workspace and every fixed child are canonically revalidated.
- Source must be an empty ordinary directory; duplicates fail without deleting existing content.
- `.git` must be a real in-source directory, never a redirection file or link.
- Linked-worktree `commondir`, object alternates, symlinks, and special source entries fail closed.
- Bounded striped locks serialize same-workspace materialization without an unbounded registry.
- Different workspaces can materialize concurrently except for an acceptable bounded stripe
  collision.
- On failure after mutation begins, cleanup removes source contents and the isolated Git
  environment only. Metadata, artifacts, temp, workspace, and sibling workspaces remain.
- Cleanup uses no-follow containment checks. Cleanup failure takes precedence and keeps the
  original materialization failure as suppressed context.
- Exceptions expose stable safe codes and generic messages; causes remain available internally.

## Architectural Decisions

- Project owns repository-level source configuration, including the currently approved exact
  commit.
- Automation Suite owns an optional repository-relative source location.
- Execution snapshots the fully resolved source identity; later catalog mutation cannot alter it.
- The first durable source is policy-approved credential-free Git HTTPS at an exact full commit.
- A local-directory resolver is test/development infrastructure only and is not user-selectable
  durable source identity.
- Workspace Manager exclusively creates, validates, and cleans unique execution workspaces under
  an operator-controlled root.
- Source Resolver materializes source without engine, persistence, lease, or cleanup authority.
- Engines receive only immutable prepared-workspace details and cannot choose arbitrary host
  paths.
- Preparation begins after fenced start commits. Filesystem, Git, engine, evidence, and cleanup
  work remains outside database transactions.
- Cleanup is bounded, idempotent, containment-verified, and secondary to authoritative outcomes.
- Restart reconciliation removes only verified abandoned directories and never resumes or retries.
- AS-023 adds no durable execution status or competing ownership model.

## Security and Persistence Summary

The workspace root is operator-controlled and cannot be a broad filesystem location. Canonical
containment, absolute/traversal rejection, link/junction defense, verified workspace markers,
bounded paths, unique identity, and pre-delete verification are mandatory.

Durable state may contain source type, sanitized repository identity, exact commit, and optional
repository-relative location. It excludes credentials, tokens, resolved secrets, workspace paths,
temporary directories, Git commands/output, and runner-local diagnostics.

## Explicit Deferrals

private Git access, retries/attempts/resume, distributed workspaces, container isolation, dynamic
plugins, user cleanup scripts, durable workspace paths, and execution resume remain separate

## AS-023F Implementation

AS-023F adds a provider-neutral application orchestration boundary that prepares an isolated
workspace before materializing its admitted immutable source. The request reuses the planned
workspace descriptor as the sole execution/workspace identity. The path-free result contains the
READY workspace descriptor, normalized materialization evidence, PREPARED state, and orchestration
timestamp.

The service cross-validates workspace identity, provider ownership, execution identity, lifecycle,
admitted source metadata, materialization workspace, source type, revision, and state. Workspace
preparation failure stops the pipeline. Materialization and downstream invariant failures release
the READY workspace. Cleanup failure takes precedence while retaining the original failure as
suppressed context, and all public messages/codes are sanitized.

`WorkspaceManager.release` now accepts READY for pre-engine compensation and internally traverses
the unchanged AS-023C graph through IN_USE and RELEASING. Spring wiring composes only the manager
and materializer ports. No engine invocation, lifecycle persistence, API, schema, Flyway, JPA, or
credential behavior was added.
