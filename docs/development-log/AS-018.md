## Objective

Define how the existing execution domain evolves into control-plane Execution Management before
implementation. The phase fixes scope, lifecycle, selection, persistence, snapshot, API,
validation, concurrency, security, testing, and AS-019 boundaries without changing production
code or database migrations.

## Existing Execution-Domain Findings

- `Execution` already exists and references Project, Environment, and `AutomationSuite`.
- Its physical suite foreign key is the transitional `execution.test_suite_id`.
- It already stores status, requester/time, start/finish time, test counters, duration, error,
  optimistic version, and audit timestamps.
- `ExecutionStatus` currently contains `PENDING`, `CLAIMED`, `RUNNING`, `PASSED`, `FAILED`,
  `CANCELLED`, and `ERROR`.
- `ExecutionStep` records ordered runtime progress and results.
- `ExecutionArtifact` records runtime evidence metadata.
- AS-018 preserves the existing physical `execution`, `execution_step`, and `execution_artifact`
  tables; it extends the existing aggregate and does not introduce a parallel execution aggregate.
- Existing Flyway migrations V2, V4, V5, and V6 own the historical execution schema and must not
  be modified.
- Environment, Automation Suite, and Automation Test Case lifecycles use ACTIVE, INACTIVE, and
  ARCHIVED; only ACTIVE resources are eligible for new execution requests.
- Automation Test Cases are independently persisted under an Automation Suite. Execution does not
  yet reference individual cases.
- Existing relationships use restrictive deletion and must continue protecting history.

## Architecture Decisions

- Extend the existing `Execution` aggregate; do not introduce a duplicate model.
- Preserve `PENDING` and add `CANCEL_REQUESTED`.
- Reject `QUEUED` as a rename.
- Keep lifecycle transitions service-controlled and expose no generic status update.
- Support `SUITE` and `TEST_CASES` selection modes.
- Introduce `execution_test_case` for immutable request intent, separate from runtime
  `execution_step`.
- Capture immutable JSONB snapshots for Environment, Automation Suite, normalized request, and
  selected cases.
- Preserve immutable request-time configuration in snapshots. Snapshots may contain
  secret-reference metadata, but must never store resolved secret values, return resolved secret
  values through APIs or error responses, or log resolved secret values.
- Preserve `test_suite` and `test_suite_id` physical names.
- Apply schema changes only through a new forward-only migration.
- Keep public execution history immutable.
- Use the existing optimistic version for cancellation and lifecycle-sensitive mutations.
- Keep AS-018 in the control plane and reserve runner processing for AS-019.

The complete execution lifecycle is:

```text
PENDING
CLAIMED
RUNNING
CANCEL_REQUESTED
PASSED
FAILED
CANCELLED
ERROR
```

Allowed transitions are:

```text
PENDING -> CLAIMED
PENDING -> CANCELLED

CLAIMED -> RUNNING
CLAIMED -> CANCEL_REQUESTED
CLAIMED -> ERROR

RUNNING -> PASSED
RUNNING -> FAILED
RUNNING -> ERROR
RUNNING -> CANCEL_REQUESTED

CANCEL_REQUESTED -> CANCELLED
CANCEL_REQUESTED -> ERROR
```

Terminal states are `PASSED`, `FAILED`, `ERROR`, and `CANCELLED`. `PENDING` is preserved,
`QUEUED` is rejected as a rename, and `CANCEL_REQUESTED` is introduced for cooperative
cancellation. Lifecycle transitions remain service-controlled.

`If-Match` is mandatory for
`POST /api/v1/projects/{projectId}/executions/{executionId}/cancel`. A missing header returns
428 Precondition Required, a malformed header returns 400 Bad Request, a stale execution version
returns 409 Conflict, and a matching version proceeds with cancellation. Cancellation races with
runner lifecycle updates, so mandatory optimistic concurrency prevents cancellation based on
stale execution state. Idempotent cancellation of `CANCEL_REQUESTED` or `CANCELLED` still requires
the current version. Cancellation of `PASSED`, `FAILED`, or `ERROR` returns 409 Conflict.

  prohibition on resolved secret exposure.

## AS-018E Implementation Evidence

### Cancellation API and concurrency

- Added `POST /api/v1/projects/{projectId}/executions/{executionId}/cancel` with an optional
  cancellation reason and the existing temporary `X-Requested-By` actor boundary.
- Requires a strong, quoted, nonnegative decimal `If-Match` version. Missing headers return
  `428 Precondition Required`; malformed values return `400 Bad Request`; stale versions return
  `409 Conflict`.
- Loads executions through the Project-scoped repository lookup before comparing versions and
  invoking the AS-018C cancellation domain behavior.
- Uses an injected UTC `Clock` for deterministic timestamps, flushes lifecycle changes in the
  transaction, and translates optimistic-lock races and invalid terminal transitions to
  `409 Conflict`.
- Preserves idempotency for current-version `CANCEL_REQUESTED` and `CANCELLED` executions without
  changing their cancellation metadata or version.
- Returns cancellation-request time, cancellation-completion time, actor, reason, and current
  version in execution responses.
